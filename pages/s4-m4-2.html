AI 能力嵌入现有业务流程的方案设计

预计 1 天模块四 · 企业级项目智能化升级

一、学习目标

  • 能够根据场景特点选择正确的嵌入模式：旁路辅助、人机协同审核，还是全自动执行。
  • 能够画出 AI 能力在现有系统中的落位图，明确 AI 模块与原系统的边界、数据流和失败兜底路径。
  • 能够设计一套"AI 输出永远不直接破坏业务数据"的防御性集成方案。

二、核心知识点

知识点 1：三种嵌入模式与选型标准

方案设计的第一个决策是"AI 站在流程的哪一侧"。旁路辅助模式：AI 只提供参考信息（推荐、提示、草稿），人做最终决定——容错差、创新期首选；人机协同模式：AI 先处理，低置信度的转人工，高置信度的直接生效——吞吐量和质量的平衡点；全自动模式：AI 直接执行写操作——只适合错误代价极低且有回滚机制的环节。

选型的判断轴是错误代价 × 置信度可度量性。金融审核错一笔可能损失百万，必须留人工闸口；垃圾邮件过滤漏判一封无关痛痒，可以全自动。常见坑：一上来就承诺全自动，结果第一次误判就把客户得罪光，项目直接被叫停。

知识点 2：落位设计与边界划分

落位设计要回答三个问题：AI 能力放在哪个层（通常是独立的 AI 网关服务，而不是塞进业务服务里，这样才能独立扩缩容和独立发布）；调用是同步还是异步（生成类任务用异步 + 通知，检索增强类可用同步但必须设短超时，一般 2-5 秒）；上下文从哪来（明确每次调用需要哪些业务字段，避免把整个订单对象塞进提示词导致 Token 爆炸和信息泄露）。

一个实用原则：AI 模块的输入输出都要有 Schema 校验。输出必须是结构化 JSON 而不是自由文本，否则下游系统根本没法消费。

知识点 3：失败兜底与渐进放权

方案里必须写清楚"AI 不可用时怎么办"。标准三件套：超时熔断（调用 AI 超过阈值就走默认逻辑）、降级策略（模型不可用时退回规则引擎或纯人工）、幂等设计（AI 重试不能产生重复业务动作）。记住这句话：用户能接受系统"变笨"，不能接受系统"变坏"。

另一个关键设计是渐进放权：上线初期置信度阈值调高（多转人工），随数据积累逐步下调，配合每周的准确率复盘。这样即使模型一开始表现一般，业务方也不会失去信心。

三、示例演示

以"客服工单自动分类 + 回复草稿"为例，展示 AI 网关的接口契约设计——注意 Schema 校验、置信度阈值和兜底分支：

# ai_gateway.py —— AI 能力网关的接口契约示例（FastAPI 风格伪代码，可直接改造使用）
from pydantic import BaseModel, Field
from typing import Literal

class ClassifyRequest(BaseModel):
    ticket_id: str
    text: str = Field(..., max_length=4000, description="工单正文，超长需上游截断")
    tenant_id: str

class ClassifyResponse(BaseModel):
    category: Literal["退款", "物流", "商品咨询", "投诉"]
    confidence: float = Field(ge=0.0, le=1.0)
    draft_reply: str | None = None   # 置信度不足时不返回草稿
    need_human: bool                 # 由网关根据阈值计算，业务方只认这个字段

CONFIDENCE_THRESHOLD = 0.75  # 上线初期高阈值，随准确率数据逐步下调

def handle(req: ClassifyRequest) -> ClassifyResponse:
    result = llm_classify(req.text)            # 内部含 5 秒超时 + 失败重试一次
    if result is None:                          # AI 不可用 → 降级为人工队列
        return need_human_fallback(req.ticket_id)
    need_human = result.confidence < CONFIDENCE_THRESHOLD
    return ClassifyResponse(**result.dict(), need_human=need_human)

业务系统只需要消费 need_human 这一个布尔字段：为 true 就进人工队列，为 false 就应用草稿并标记分类。业务代码完全不感知模型细节，将来换模型、换阈值都不用改业务侧。

💡 提示：把"置信度阈值"做成配置中心里的动态参数，是渐进放权最便宜的实现方式。调参不用发版，出问题秒级回退。

四、实践任务

  1. 任务 1：为上一节选出的 Top 场景选择嵌入模式，写 200 字论证：为什么不是另外两种模式。
  2. 任务 2：画一张落位图（可用 draw.io 或纸笔拍照），标出 AI 网关、原业务服务、数据库、人工队列四个组件及数据流向。
  3. 任务 3：定义 AI 网关的请求/响应 Schema，字段不少于 5 个，包含置信度与人工兜底标记。
  4. 任务 4（进阶，可选）：写出降级方案文档一节，覆盖"模型超时""模型返回非法 JSON""配额耗尽"三种故障场景各自的处理动作。

  • AI 的输出是否有结构化校验，业务侧是否可以完全不感知模型细节？
  • 我的阈值是否做成了可动态调整的配置，而不是硬编码？
