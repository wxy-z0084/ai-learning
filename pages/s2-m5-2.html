阶段二 · 智能体开发

日志、监控与异常处理

预计 0.5 天模块五 · 企业级开发与部署

一、学习目标

  • 能够用标准库 logging 配置分级日志，并输出便于检索的结构化 JSON 日志。
  • 能够为模型调用设计"异常分级 + 有限重试 + 降级"策略，区分可重试错误与不可重试错误。
  • 能够定义关键业务指标（调用次数、延迟、token 消耗、失败率）并说明如何采集与告警。
  • 能够给一次智能体失败排查写出完整链路：从 trace_id 到日志、指标与告警的定位路径。

二、核心知识点

知识点 1：结构化日志——为检索而写

print 调试在本地可行，线上等于没有：没有时间戳、没有级别、无法按请求过滤。Python logging 提供 DEBUG/INFO/WARNING/ERROR/CRITICAL 五级与 logger 层级继承，根 logger 统一配置 handler 与 formatter 即可全局生效。企业级做法是把日志输出为一行一条的 JSON，字段固定包含 ts、level、logger、msg、trace_id、user_id、tokens、latency_ms、exc，这样可以直接被 Loki、ELK、云日志服务摄取并按字段检索。

常见坑：在库代码里配置 root logger（应只在应用入口配置一次）；日志里打印完整 prompt 导致泄露与超长（应截断并脱敏）；异常不带 exc_info=True，丢掉了堆栈。

知识点 2：智能体异常分级与重试

模型与网络调用的错误要分两类：可重试（超时、429 限流、5xx 服务端错误、连接中断）应按指数退避重试 2-3 次；不可重试（401 密钥无效、400 参数错误、内容策略拒绝）应立刻失败并告警。重试必须带上限与总超时预算，否则一次抖动会放大成雪崩。关键路径还要准备降级：模型不可用时返回缓存答案或友好提示，而不是让整个服务 500。

知识点 3：指标与可观测性三支柱

日志回答"发生了什么"，指标（Metrics）回答"现在整体怎么样"，链路追踪（Tracing）回答"慢在哪一环"。智能体服务至少暴露四类指标：QPS/请求总数、P95 延迟、模型 token 消耗、错误率，再加业务指标如"回答含引用比例"。指标通常由应用以 Prometheus 格式暴露（或经 OpenTelemetry 导出），配合 Grafana 看板与阈值告警（如 5 分钟错误率 > 5% 触发通知）。trace_id 贯穿一次请求的全部日志，是排查的抓手。

三、示例演示

示例一：JSON 结构化日志配置，放在应用入口调用一次：

# src/agent_hub/logging_config.py
import datetime
import json
import logging
import sys


class JsonFormatter(logging.Formatter):
    def format(self, record: logging.LogRecord) -> str:
        payload = {
            "ts": datetime.datetime.now(datetime.timezone.utc).isoformat(),
            "level": record.levelname,
            "logger": record.name,
            "msg": record.getMessage(),
            "trace_id": getattr(record, "trace_id", "-"),
            "latency_ms": getattr(record, "latency_ms", None),
        }
        if record.exc_info:
            payload["exc"] = self.formatException(record.exc_info)
        return json.dumps(payload, ensure_ascii=False)


def setup_logging(level: str = "INFO") -> None:
    handler = logging.StreamHandler(sys.stdout)
    handler.setFormatter(JsonFormatter())
    root = logging.getLogger()
    root.handlers[:] = [handler]
    root.setLevel(level)

示例二：带指数退避的重试装饰器，用于包住模型调用：

# src/agent_hub/retry.py
import functools
import time

RETRYABLE = (TimeoutError, ConnectionError)


def retry(times: int = 3, base_delay: float = 1.0):
    def deco(fn):
        @functools.wraps(fn)
        def wrapper(*args, **kwargs):
            for attempt in range(times):
                try:
                    return fn(*args, **kwargs)
                except RETRYABLE as e:
                    if attempt == times - 1:
                        raise
                    delay = base_delay * (2 ** attempt)
                    time.sleep(delay)
                    print(f"重试 {attempt + 1}/{times}，{delay}s 后再试: {e}")
        return wrapper
    return deco


@retry(times=3)
def call_llm(prompt: str) -> str:
    ...  # 真实的模型调用
💡 提示：日志里务必带上 trace_id（可用 uuid4().hex[:8] 生成并放进 contextvar），出问题时用它串起一次请求的全部日志；401/400 这类错误重试没有意义，会白白消耗预算并触发风控。

四、实践任务

  1. 任务 1：在你的智能体项目入口接入 setup_logging，把所有 print 替换为带上下文字段的 logger 调用，确认输出为一行一条 JSON。
  2. 任务 2：实现 retry 装饰器包裹模型调用，人为注入超时与 401 两类错误，验证前者会重试、后者立即失败。
  3. 任务 3：定义并记录四个核心指标（请求总数、P95 延迟、token 消耗、错误率），写出你打算如何统计与告警的方案文档（一段话即可）。
  4. 任务 4（进阶，可选）：接入 OpenTelemetry，为一次问答请求生成 trace，观察日志中的 trace_id 与 trace 查询结果是否对应。

五、推荐资源

  • 📖 Python logging 官方文档 — 掌握 logger/handler/formatter/filter 与 logging.config 配置方式。
  • 📖 OpenTelemetry 官方文档 — 指标与链路追踪的行业标准，先读概念页再看 Python SDK。
  • 📖 Prometheus 官方文档 — 指标采集、PromQL 查询与告警规则的入门路径。
  • 📖 structlog — Python 结构化日志的流行库，可作为标准 logging 的增强。
  • 🛠 Grafana — 把日志、指标、追踪放在同一看板上做联动排查。
