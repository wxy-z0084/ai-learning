阶段四 · 业务解决方案

限流、熔断与降级策略

预计 0.5 天模块五 · 高并发系统落地

一、学习目标

  • 能够区分并选型四种限流算法（固定窗口、滑动窗口、漏桶、令牌桶），说清各自的适用场景。
  • 能够使用 Sentinel 或 Resilience4j 为关键接口配置熔断规则，并解释慢调用比例与异常比例的差异。
  • 能够为一个高并发接口设计完整的三级兜底：限流拒绝 → 熔断降级 → 静态兜底页。

二、核心知识点

知识点 1：限流——守住系统的第一道闸门

固定窗口计数最简单：每分钟限 1000 次，但窗口切换瞬间可能放进来 2000 次（临界突发），这是它的原罪；滑动窗口把窗口切成小格子滚动统计，解决了临界问题，是 Sentinel 默认实现；漏桶以恒定速率漏水，输出绝对平滑，适合保护下游"节奏敏感"的服务，但突发流量要么排队要么直接丢；令牌桶按速率生成令牌、允许积累，兼顾了平滑与允许合理突发，是业界默认选择（Guava RateLimiter 即此类）。

限流维度要分层部署：网关层按 IP/用户全局限流，服务层按接口限流，热点参数按商品 ID、账号 ID 限流（防黄牛刷票最有效）。常见坑：只在一处限流，网关挡住了但服务间内部调用没有二次防护，一旦某服务雪崩仍会拖垮全站。

知识点 2：熔断——防止故障扩散

熔断的逻辑类似电路保险丝：当下游错误率或慢调用比例超过阈值，直接在本地快速失败，不再真的发起调用，给下游喘息和恢复的时间。慢调用比例规则适合"响应变慢才是前兆"的场景（如数据库连接池将满），异常比例规则适合"报错即故障"的场景（如下游返回 5xx）。熔断后系统会进入半开状态：放少量探测请求试探，成功则恢复，失败则继续熔断。

关键经验：熔断阈值不是越低越好——设 1% 会导致轻微抖动就大面积熔断，设 30% 又形同虚设。要根据历史监控数据的错误率分布来定，并且给每个规则配一条告警，熔断本身也是需要被知道的事件。

知识点 3：降级——用户体验的最后防线

降级回答"系统不能正常服务时，给用户看什么"。设计原则是保核心、弃周边：保住下单支付主链路，牺牲推荐、评论、积分等旁路功能。降级方式按侵入程度排列：配置开关关闭某功能 → 读缓存兜底（返回 10 分钟前的数据）→ 静态兜底页（活动太火爆，请稍后再试）。对 AI 场景，还要加上"模型不可用退回规则引擎"的降级（在模块四方案设计中已铺垫）。

所有降级开关必须集中在配置中心并支持秒级生效，否则大促当晚你在改代码还是在改配置，直接决定事故等级。

三、示例演示

示例一：Sentinel 规则配置（JSON 格式，可直接通过 Nacos 推送到运行中的应用，实现规则动态化）：

[
  {
    "resource": "/api/order/create",
    "grade": 1,                     // 1=QPS 限流，0=并发线程数
    "count": 200,                   // 单机 QPS 上限
    "strategy": 0,
    "controlBehavior": 0,           // 0=快速失败 1=Warm Up 2=排队等待
    "clusterMode": false
  },
  {
    "resource": "/api/ai/chat",
    "grade": 0,                     // 熔断规则：按并发数保护 AI 服务
    "count": 50,
    "slowRatioThreshold": 0.5,      // 慢调用比例阈值：50%
    "timeWindow": 30,               // 熔断持续 30 秒后进入半开探测
    "minRequestAmount": 20          // 统计窗口内至少 20 次请求才触发判定
  }
]

示例二：令牌桶限流的最小可用实现（Guava，一行代码嵌进接口入口）：

import com.google.common.util.concurrent.RateLimiter;

public class OrderRateLimiter {
    // 每秒发放 200 个令牌，多余的调用会阻塞等待（最多等 200ms）
    private static final RateLimiter limiter = RateLimiter.create(200);

    public static boolean tryAcquire() {
        return limiter.tryAcquire(200, java.util.concurrent.TimeUnit.MILLISECONDS);
    }
}

// 使用：放行失败直接返回限流提示，绝不能默默排队到超时
if (!OrderRateLimiter.tryAcquire()) {
    return Result.tooManyRequests("系统繁忙，请 1 分钟后重试");
}
💡 提示：限流返回的信息不要泄露实现细节（别说"令牌桶耗尽"），给用户一句可操作的提示 + 一个可预期的等待时间，对客服压力的缓解比技术优化还大。

四、实践任务

  1. 任务 1：用表格对比四种限流算法的突发处理能力、平滑性、实现复杂度，各写一个你业务里的候选场景。
  2. 任务 2：本地跑起 Sentinel Dashboard（或 Resilience4j），为一个模拟接口配置 QPS 限流并验证超过阈值时的返回。
  3. 任务 3：为该接口再配置一条"慢调用比例 50%"熔断规则，用 sleep 模拟慢响应，观察快速失败与半开恢复的过程。
  4. 任务 4（进阶，可选）：设计一份降级预案表，列出 5 个非核心功能，各自写明降级动作、开关所在配置项和预期用户体验变化。

六、自检清单

  • 我能说出令牌桶和漏桶的核心区别以及各自该用在哪类服务前吗？
  • 我的关键接口是否都有限流和熔断两道防线？
  • 我的降级开关是否都在配置中心，能否 1 分钟内生效？
  • 限流触发后，用户看到的提示是否清晰、可操作？
