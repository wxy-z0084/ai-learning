流式响应（SSE / WebSocket）

预计 1 天模块二 · FastAPI

一、学习目标

  • 能够说清一次性 JSON 响应与流式响应的差异，解释为什么大模型对话普遍用流式（首字延迟体验）。
  • 能够实现基于 SSE（Server-Sent Events） 的单向服务器推送：正确构造 text/event-stream 格式与事件字段。
  • 能够实现 WebSocket 双向通信：完成握手、收发消息、处理断线与心跳。
  • 能够按需求在 SSE 与 WebSocket 之间做出选择，并处理代理缓冲、连接生命周期等落地坑。

二、核心知识点

知识点 1：为什么流式——首字延迟与体验

普通接口是「请求 → 服务端处理完 → 一次性返回」。调用大模型时完整生成可能要 10 秒，用户会盯着空白页面等 10 秒；流式响应则是在一次 HTTP 连接上分批、增量地把数据推给客户端，第一个 token 一生成（TTFT，首字延迟）就先发出去，观感从「卡死」变成「打字机效果」，同时降低用户中途放弃的概率。流式也适合大文件下载、日志实时查看、进度上报等场景。核心判断：数据是「陆续产生、单向下发」→ 用流式；「一次调用一次返回」用普通 JSON 即可，别为了流而流。

知识点 2：SSE 原理与格式

SSE（Server-Sent Events）基于普通 HTTP 长连接，服务端把响应头设为 Content-Type: text/event-stream，随后持续写入以换行分隔的事件文本，浏览器端用原生 EventSource 接收，断线时自动重连（可配合 id 字段与 Last-Event-ID 续传）。文本协议每行以冒号前缀区分字段：data: 负载（多行 data 累积为一条消息，必须以空行结尾）、event: 事件名（默认 message）、id: 事件 ID、retry: 重连间隔毫秒。注意：data 内容若含换行必须拆成多行 data，JSON 通常放在单行 data 中再由客户端 JSON.parse。对比轮询：SSE 是一次连接持续推、无重复请求开销、延迟低；对比 WebSocket：SSE 只能服务器→客户端单向，且天然走 HTTP，更容易穿透代理与鉴权（可复用 Cookie/Header），EventSource 不支持自定义请求头是它的一个限制。

知识点 3：FastAPI 中实现 SSE

用 StreamingResponse（来自 fastapi.responses，Starlette 提供）返回一个异步生成器：yield 出去的每一段都会立刻刷给客户端。生成器里可以 await 下游服务（如流式调用大模型 API），天然兼容 asyncio。要点：① 响应头显式设置 text/event-stream；② 每条消息结尾写 \n\n（事件分隔符）；③ 关掉中间层缓冲，Nginx 需要 X-Accel-Buffering: no 头或 proxy_buffering off，否则会攒批导致「不流」；④ 客户端断开时生成器会抛 CancelledError/GeneratorExit，要在 finally 里释放下游资源（关闭模型流、取消任务），否则泄漏连接。

知识点 4：WebSocket 双向通信

WebSocket 先通过 HTTP Upgrade 握手升级连接，之后在同一 TCP 连接上全双工通信，两端随时互发消息，没有 HTTP 头的反复开销——适合聊天室、协同编辑、实时双向 agent 会话。FastAPI 用 @app.websocket("/ws") 定义，路径参数/依赖注入与 HTTP 路由一致；通过 await websocket.receive_json() 接收、await websocket.send_json() 发送，循环中处理 WebSocketDisconnect 异常实现退出。工程要点：连接要登记在线表并加锁维护；定期 ping/pong 心跳 探活；服务重启前向客户端发关闭码让它重连；鉴权可放在握手阶段（query 参数或 Cookie 校验，不通过就 accept 后立即 close）。

选型口诀：单向推送、走 HTTP、要自动重连 → SSE；双向交互、高频小消息 → WebSocket；一问一答小数据 → 普通 REST。

三、示例演示

示例一：SSE 流式输出「打字机」回答（pip install fastapi uvicorn httpx，运行后访问 /docs 或前端用 EventSource 连 /chat-stream）：

import asyncio
import json
from fastapi import FastAPI
from fastapi.responses import StreamingResponse

app = FastAPI()

async def fake_llm(question: str):
    """模拟流式生成：真实场景替换为对大模型 API 的流式调用"""
    for word in "这是一个流式回答，逐字返回以降低首字延迟。".split("，"):
        await asyncio.sleep(0.3)          # 模拟生成耗时
        yield word

@app.post("/chat-stream")
async def chat_stream(question: str = "你是谁"):
    async def event_source():
        # SSE 头 + 禁用反向代理缓冲，保证逐条刷出
        yield "retry: 3000\n\n"            # 客户端断线后 3s 重连
        async for piece in fake_llm(question):
            payload = json.dumps({"delta": piece}, ensure_ascii=False)
            yield f"data: {payload}\n\n"   # 事件分隔必须是两个换行
        yield f"data: {json.dumps({'delta': '[DONE]'})}\n\n"

    return StreamingResponse(
        event_source(),
        media_type="text/event-stream",
        headers={"Cache-Control": "no-cache",
                 "X-Accel-Buffering": "no"},
    )

示例二：WebSocket 双向会话与断线处理：

from fastapi import FastAPI, WebSocket, WebSocketDisconnect

app = FastAPI()

@app.websocket("/ws/chat")
async def ws_chat(ws: WebSocket):
    await ws.accept()                       # 完成握手
    try:
        while True:
            msg = await ws.receive_json()   # {"text": "..."}
            if msg.get("text") == "ping":
                await ws.send_json({"type": "pong"})
                continue
            # 回声式应答，真实项目在此调用 agent 并分片回复
            await ws.send_json({
                "type": "chunk",
                "data": f"已收到：{msg['text']}",
            })
    except WebSocketDisconnect:
        print("客户端断开，清理该连接的会话资源")
    except Exception:
        await ws.close(code=1011)           # 异常关闭并告知原因
💡 提示：前端接收 SSE 极简——new EventSource('/chat-stream') 后 onmessage 即可（POST 型需用 fetch + ReadableStream 读取）。调试时用 curl -N http://127.0.0.1:8000/chat-stream（-N 关闭 curl 自身缓冲）可直接看到逐条输出。
