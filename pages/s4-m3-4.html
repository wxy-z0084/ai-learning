共享记忆与状态管理

预计 0.5 天模块三 · 多智能体开发

一、学习目标

  • 能够区分对话内记忆、会话持久化、长期语义记忆三层，并说明各自的数据形态与生命周期。
  • 能够用 LangGraph 的 checkpointer + thread_id 实现会话状态持久化与断点续跑。
  • 能够设计一个共享记忆库（向量检索 + 元数据过滤），支持多智能体按权限读写。
  • 能够给出上下文预算与摘要裁剪策略，避免多轮协作中上下文爆炸。

二、核心知识点

知识点 1：三层记忆模型

第一层：对话内记忆（Working Memory）就是当前 messages 列表——模型每次推理看到的全部内容，随轮次线性增长，超出窗口即丢失最早信息。它由调用方管理（保留几条、裁剪几条由你决定）。第二层：会话状态（Session/Thread State）指可序列化的结构化数据（表单字段、任务进度、中间产物），存储在数据库里，用 thread_id 索引；LangGraph 的 checkpointer 就是这一层的标准实现——每次图执行结束自动把 State 存档，再次 invoke 同 thread_id 时恢复现场，天然获得"会话恢复""人工审批中断后续跑"能力。

第三层：长期记忆（Long-term Semantic Memory）是跨会话沉淀的知识：用户偏好、项目事实、历史决策。实现通常是"向量化 + 检索"：文本经 embedding 模型转成向量存入向量库（pgvector、Chroma、Milvus），每次推理前按当前任务检索 top-k 相关条目注入 prompt。三层的写入策略不同：第一层要控制体积，第二层要保证一致与可回滚，第三层要保证质量（脏记忆一旦入库会持续毒害后续所有会话，必须有审核与过期机制）。

知识点 2：共享记忆的并发与冲突

多智能体共享一个记忆库时，单会话记忆的管理问题被放大。三类典型冲突：写-写冲突（两个智能体同时更新同一条"项目状态"，后写覆盖前写）——对策是给记忆加版本号/时间戳，写入用乐观锁，或按主题分片让不同角色写不同空间；读到脏记忆（A 写入半成品结论，B 检索到就当事实引用）——对策是记忆条目带 status 字段（draft / confirmed），检索默认只返回 confirmed，由评审角色负责 draft 升级；矛盾记忆累积（上轮说方案选 A，这轮说选 B，两条都躺在库里）——对策是写入前做相似度检查，高相似且结论相反时走"替换"而非"追加"，并保留历史版本供审计。

访问控制也要设计：不是每个角色都能读全部记忆——评审员需要看到全部草稿，而执行者只该看到确认后的指令。工程上最简做法是按 visibility 标签过滤检索；严肃做法是每个角色一个记忆命名空间，由 Supervisor 负责跨空间搬运。

知识点 3：上下文预算与裁剪

多智能体系统里 token 成本的头号杀手是无节制的上下文累积。做法是给每次调用设上下文预算：先确定预算（如 8K tokens），分配比例大致为 系统提示词 20% / 检索到的记忆 20% / 当前任务输入 40% / 预留输出 20%，然后从大到小裁剪。裁剪手段按信息价值排序：直接丢弃最老的中间过程消息（保留首条与最近 N 条）、滚动摘要（用一次廉价 LLM 调用把 20 轮历史压成 300 字摘要——摘要里必须保留数字、决策与未决问题，这是最容易丢的信息）、外部化（把大文档落盘只传路径/ID，运行时按需检索）。实践技巧：把"哪些字段绝不允许被摘要"写成规则（金额、ID、验收标准），并在裁剪后断言关键字段仍在上下文里——否则静默丢失会在若干轮之后才以"AI 忽忽悠悠说错话"的形式爆发。

三、示例演示

示例一：LangGraph checkpointer 实现会话状态持久化（模拟"审批中断 → 恢复续跑"场景，pip install langgraph langgraph-checkpoint-sqlite）：

from langgraph.graph import StateGraph, END
from langgraph.checkpoint.sqlite import SqliteSaver
from typing import TypedDict

class OrderState(TypedDict):
    order_id: str
    approved: bool
    log: list

def prepare(state: OrderState) -> OrderState:
    return {"log": state["log"] + [f"{state['order_id']} 材料已准备，等待人工审批"]}

def approve(state: OrderState) -> OrderState:
    # approved 由外部审批系统在恢复会话时写入 State（interrupt 机制或外部更新）
    tag = "已批准" if state["approved"] else "未批准"
    return {"log": state["log"] + [f"审批结果：{tag}"]}

def route(state: OrderState) -> str:
    return END if state["approved"] else "wait"      # 未批准：停在此处等人

def wait(state: OrderState) -> OrderState:
    return {"log": state["log"] + ["挂起中，等待审批信号"]}

g = StateGraph(OrderState)
g.add_node("prepare", prepare)
g.add_node("approve", approve)
g.add_node("wait", wait)
g.set_entry_point("prepare")
g.add_edge("prepare", "approve")
g.add_conditional_edges("approve", route, {"wait": "wait", END: END})
g.add_edge("wait", END)

with SqliteSaver.from_conn_string("checkpoints.db") as memory:
    app = g.compile(checkpointer=memory)
    cfg = {"configurable": {"thread_id": "order-1001"}}   # 会话主键
    app.invoke({"order_id": "1001", "approved": False, "log": []}, cfg)

    # —— 模拟几小时后，审批人在另一个进程点击"批准"——
    with SqliteSaver.from_conn_string("checkpoints.db") as mem2:
        app2 = g.compile(checkpointer=mem2)
        snap = app2.get_state(cfg)                      # 恢复到中断处的状态
        snap.values["approved"] = True
        app2.update_state(cfg, snap.values)             # 写回审批结果
        print(app2.invoke(None, cfg)["log"])            # 从断点继续执行到结束
💡 checkpointer 同时也是"状态管理审计日志"：每个 checkpoint 都是一次图执行结束时的完整 State 快照，出问题可逐帧回放。生产环境把 SqliteSaver 换成 PostgresSaver 即可多副本共享。

示例二：轻量共享记忆库——按语义检索、带状态过滤与版本管理（向量部分示意为关键词打分，生产替换为 embedding 即可）：

import json, time, uuid

mem_file = "shared_memory.jsonl"

def write_memory(actor: str, topic: str, content: str, status="draft", visibility="all"):
    rec = {"id": str(uuid.uuid4()), "actor": actor, "topic": topic,
           "content": content, "status": status, "visibility": visibility,
           "created_at": time.time(), "version": 1}
    with open(mem_file, "a", encoding="utf-8") as f:
        f.write(json.dumps(rec, ensure_ascii=False) + "\n")
    return rec["id"]

def search_memory(query: str, limit=3):
    """检索：按主题词打分 + 只返回 confirmed（防脏记忆）"""
    recs = [json.loads(l) for l in open(mem_file, encoding="utf-8")]
    hits = [r for r in recs if r["status"] == "confirmed"
            and (r["topic"] in query or any(w in r["content"] for w in query.split()))]
    hits.sort(key=lambda r: r["created_at"], reverse=True)
    return hits[:limit]

def confirm_memory(mem_id: str, reviewer: str):
    """评审角色把草稿升级为已确认——draft 永远不会被检索到"""
    lines = []
    for l in open(mem_file, encoding="utf-8"):
        r = json.loads(l)
        if r["id"] == mem_id:
            r["status"], r["version"] = "confirmed", r["version"] + 1
            r["confirmed_by"] = reviewer
        lines.append(json.dumps(r, ensure_ascii=False))
    open(mem_file, "w", encoding="utf-8").write("\n".join(lines) + "\n")

# 用法：writer 写草稿 -> reviewer 确认 -> 之后所有角色检索到的都是确认过的结论
mid = write_memory("writer", "选型结论", "消息队列选用 Kafka，因需分区顺序性与回溯消费")
confirm_memory(mid, "reviewer")
for m in search_memory("消息队列选型结论"):
    print(m["actor"], ":", m["content"])

四、实践任务

  1. 任务 1：跑通示例一：首次 invoke 后"杀掉"进程，重新启动再用同 thread_id 恢复，验证 log 完整续接；把 thread_id 换成新值确认是全新会话。
  2. 任务 2：给示例二加并发写入测试：两个线程同时写入同一 topic 并互相确认，观察是否出现矛盾结论，用"相似主题替换"策略修复。
  3. 任务 3：为你的一个多智能体流程写上下文预算表：列出每次调用的 prompt 组成与 token 配额，并实现裁剪后"关键数字仍在场"的断言。
  4. 任务 4（进阶，可选）：把示例二的记忆库换成 Chroma + embedding 检索（pip install chromadb），对比关键词检索与语义检索在模糊问题上的命中率差异。
