分层架构设计（Controller-Service-DAO）

预计 1 天模块二 · 企业级单体项目开发

一、学习目标

  • 学完本节后，你能够准确说出 Controller、Service、DAO 三层各自的职责边界与单向依赖规则，并指出常见越层调用问题。
  • 你能够为一个新业务模块设计规范的包结构，并明确 DTO、Entity、VO 三类对象的转换链路。
  • 你能够独立写出一个带事务的增删改查接口的三层代码，保证事务边界落在 Service 层。
  • 你能够借助 ArchUnit 或 Code Review 清单，检查并纠正项目中的分层违规。

二、核心知识点

知识点 1：为什么要分层，依赖只能单向

分层的本质是按职责切分复杂度：请求解析、业务规则、数据存取是三种完全不同的变化频率，把它们混在一个类里，改任何一处都要重新理解全部代码。企业级单体项目通常采用三层架构：Controller（表现层）负责接收参数、校验、调用服务、组织返回值；Service（业务层）承载业务规则与事务边界；DAO（持久层，也叫 Mapper）只负责与数据库打交道。

依赖方向必须是单向的：Controller → Service → DAO，反向依赖（DAO 调 Service、Controller 直接调 Mapper）几乎一定是设计错误。判断口诀是：Controller 里不写 if 业务分支，Service 里不出现 HttpServletRequest，DAO 里不出现业务名词之外的事务注解。

知识点 2：三层职责详解与对象转换

Controller 层的代码应当"薄"：接收 DTO（Data Transfer Object，接口入参），用 Bean Validation 注解完成参数校验，调用一个 Service 方法，把返回的 Entity 或领域对象转换为 VO（View Object，接口出参）后包装返回。不要在 Controller 里注入 Mapper，也不要在 Controller 上加 @Transactional——事务应该由 Service 方法的完整业务动作来界定，一个 Service 方法对应一个原子业务操作。

Service 层是唯一可以写业务分支和编排多个 DAO 调用的地方。返回给前端的对象尽量不要直接是数据库 Entity：Entity 加了字段（如内部备注）就会被顺手序列化出去，造成越权泄露。规范做法是 DTO → Entity → VO 三段转换，可用 MapStruct 或 BeanUtils 完成，字段多时建议显式映射以便日后审计。

知识点 3：包结构组织与常见坑

常见组织方式是按层分包（controller / service / mapper / domain），团队规模大时也可按业务模块分包再在模块内分层，两种方式各有取舍，但同一个项目只用一种。典型坑包括：把 MyBatis 的分页查询直接塞进 Controller（数据访问逻辑泄漏到表现层）、Service 之间互相循环依赖（通常说明缺少第三个编排 Service 或职责划分不清）、一个几百行的"上帝 Service"（应按子领域拆分）。此外注意 DTO 与 Entity 同名同包导致 import 混乱，是新手最常犯的低级错误。

三、示例演示

下面是一个订单模块的标准三层代码，可直接作为新项目的骨架参考：

// 1) 实体：与数据库表 t_order 一一对应
@Data
@TableName("t_order")
public class Order {
    @TableId(type = IdType.ASSIGN_ID)
    private Long id;
    private Long userId;
    private BigDecimal amount;
    private Integer status;      // 0 待支付 1 已支付
    private LocalDateTime createTime;
}

// 2) DAO：只做数据访问，继承 MyBatis-Plus 的 BaseMapper 即可
public interface OrderMapper extends BaseMapper<Order> {
}

// 3) Service：业务逻辑 + 事务边界
@Service
@RequiredArgsConstructor
public class OrderService {
    private final OrderMapper orderMapper;

    public Order detail(Long id) {
        Order order = orderMapper.selectById(id);
        if (order == null) {
            throw new BizException("订单不存在:" + id);
        }
        return order;
    }

    @Transactional(rollbackFor = Exception.class)
    public Long create(OrderCreateDTO dto) {
        Order order = new Order();
        BeanUtils.copyProperties(dto, order);
        order.setStatus(0);
        order.setCreateTime(LocalDateTime.now());
        orderMapper.insert(order);
        return order.getId();
    }
}

// 4) Controller：只做参数校验、调用、出参转换
@RestController
@RequestMapping("/orders")
@RequiredArgsConstructor
public class OrderController {
    private final OrderService orderService;

    @PostMapping
    public R<Long> create(@Valid @RequestBody OrderCreateDTO dto) {
        return R.ok(orderService.create(dto));
    }

    @GetMapping("/{id}")
    public R<OrderVO> detail(@PathVariable Long id) {
        OrderVO vo = new OrderVO();
        BeanUtils.copyProperties(orderService.detail(id), vo);
        return R.ok(vo);
    }
}

对应的包结构与依赖方向如下（上层依赖下层，禁止反向）：

com.example.mall
├── controller      // 参数接收、校验、DTO/VO 转换
├── service         // 业务逻辑、事务边界
│   └── impl
├── mapper          // DAO：只写 SQL 与数据存取
├── domain
│   ├── entity      // 数据库实体
│   ├── dto         // 接口入参
│   └── vo          // 接口出参
├── common          // 统一响应 R、全局异常、常量
└── config          // 配置类
💡 提示：评审时可先搜代码里的 import——Controller 的 import 列表中若出现 Mapper、SqlSession，或 DAO 中出现 HttpServletRequest，即可判定为分层违规。

四、实践任务

  1. 任务 1：按上面的包结构新建一个 Spring Boot 工程骨架，把 common、config、domain 目录和统一响应类建好，做到新模块复制即用。
  2. 任务 2：实现"文章管理"的增删改查接口（含分页查询），要求 Controller 不注入任何 Mapper，Service 方法上正确标注事务。
  3. 任务 3：为任务 2 补上 DTO 与 VO 两个对象，字段做差异化设计（如 VO 多返回作者昵称、DTO 不允许前端传 status），并说明每个字段差异的原因。
  4. 任务 4（进阶，可选）：引入 ArchUnit 编写一条架构测试，断言 controller 包不得依赖 mapper 包，让分层规则在 CI 中自动失败。
