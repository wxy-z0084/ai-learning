分库分表（ShardingSphere）

预计 1 天模块二 · 分布式方案

一、学习目标

  • 能够判断一个业务是否真的需要分库分表，并选择分片键与分片策略（哈希取模 / 范围 / 一致性哈希）。
  • 能够用 ShardingSphere-JDBC 写出分库分表配置，说明分片算法、绑定表、广播表的作用。
  • 能够处理分片后的典型难题：跨分片排序分页、全局唯一 ID、跨分片 JOIN 与分布式事务。
  • 能够设计不停机扩容与数据迁移的基本步骤（双写、校验、切读）。

二、核心知识点

知识点 1：什么时候该分、怎么选分片键

分库分表是"最后手段"：单表行数过亿、单库磁盘或连接数成为瓶颈，且加索引、读写分离、归档历史数据、升级硬件都已无效时才考虑。不分片的代价远小于分片的代价——分片后所有不带分片键的查询都要广播到全分片，运维复杂度陡增。很多公司单表 5000 万行 + 读写分离就能再撑几年，先榨干这些手段。

分片键（sharding key）的选择决定成败，原则是高频查询条件里必带该字段：订单表用 user_id（按用户查订单是最高频场景），明细表用 order_id。分片键选错，等于把单库问题变成 N 个库的全量扫描问题。策略上，哈希取模（user_id % 库数）数据分布均匀但扩容要迁移；范围分片（按月份）扩容方便但热点集中。实践中常见"库内哈希、库间范围"的混合策略：库按日期分、表按 ID 哈希。另一个铁律：分片键上的等值条件能路由到单分片，其余条件只能全分片执行，接口设计时就要保证用户请求必带分片键。

知识点 2：ShardingSphere 的核心概念

Apache ShardingSphere 是 Apache 顶级项目，提供三种形态：JDBC（Java 客户端内嵌分片引擎，无代理层、性能最好）、Proxy（独立数据库代理，兼容 MySQL/PostgreSQL 协议，多语言可用）、Sidecar（面向 Service Mesh 的无代理模式，尚不成熟）。核心配置由四部分组成：数据源（真实数据库连接）、逻辑表与真实表（代码里操作逻辑表 orders，引擎路由到 orders_0…orders_n）、分片规则（分片键 + 分片算法）、绑定表（orders 与 order_items 用同一分片键，使跨表 JOIN 只在同分片内发生，避免笛卡尔积）。

另外两个高频概念：广播表（如字典表，每个分片都存全量副本，JOIN 时无网络开销）；分布式主键（分片后单库自增 ID 必然冲突，ShardingSphere 内置 SNOWFLAKE 与 UUID 算法，雪花 ID 生成器要解决时钟回拨问题）。读写分离可与分片叠加：分片规则里为每个分库配置主从数据源与负载均衡策略。

知识点 3：分片后的四大难题与对策

跨分片分页排序：查"所有用户的第 10 页最新订单"必须先在每个分片取 offset+limit 条再归并排序，深翻页（offset 10 万）代价极高——业务上应改用游标分页（WHERE id < last_id ORDER BY id DESC LIMIT 20），彻底消灭 offset。

跨分片聚合：COUNT/AVG 可归并，但 DISTINCT、GROUP BY 大表会拖慢查询，冷数据建议走离线数仓。跨分片事务：本地事务失效，可用 ShardingSphere 的 XA 或 SEC（ShardingSphere-Embedded-Transaction，Seata 内置）模式，或干脆用前一节的最终一致性方案。数据迁移与扩容：不停机方案分四步——双写新旧分片、按分片键重新路由读、历史数据迁移比对、下线旧分片；迁移期间务必保证"新数据双写、旧数据可回放"。

三、示例演示

示例一：ShardingSphere-JDBC 5.x 的 YAML 规则——orders 表按 user_id 哈希分 2 库 × 4 表，order_items 作为绑定表同键分片，dict_info 为广播表：

# application-sharding.yaml（Spring Boot 内使用 spring.shardingsphere 前缀）
spring:
  shardingsphere:
    datasource:
      names: ds0,ds1
      ds0:
        type: com.zaxxer.hikari.HikariDataSource
        driver-class-name: com.mysql.cj.jdbc.Driver
        jdbc-url: jdbc:mysql://10.0.0.11:3306/orders_db?useSSL=false
        username: app
        password: ***
      ds1:
        type: com.zaxxer.hikari.HikariDataSource
        driver-class-name: com.mysql.cj.jdbc.Driver
        jdbc-url: jdbc:mysql://10.0.0.12:3306/orders_db?useSSL=false
        username: app
        password: ***
    rules:
      sharding:
        tables:
          orders:                              # 逻辑表
            actual-data-nodes: ds$->{0..1}.orders_$->{0..3}
            table-strategy:
              standard:
                sharding-column: user_id
                sharding-algorithm-name: orders-mod
            key-generate-strategy:            # 分布式主键
              column: order_id
              key-generator-name: snowflake
          order_items:                         # 绑定表：与 orders 同键，JOIN 不跨片
            actual-data-nodes: ds$->{0..1}.order_items_$->{0..3}
            table-strategy:
              standard:
                sharding-column: user_id
                sharding-algorithm-name: orders-mod
        broadcast-tables: [dict_info]
        sharding-algorithms:
          orders-mod:
            type: HASH_MOD                    # 取模分片
            props:
              sharding-count: 4
        key-generators:
          snowflake:
            type: SNOWFLAKE

配置生效后，业务代码完全不感知分片，正常的 MyBatis/JPA 查询会自动路由；但 SELECT * FROM orders WHERE order_id = ?（不带 user_id）会广播到全部 8 张表——这正是"分片键必须出现在高频查询中"的原因。

💡 验证路由是否正确：开启 sql-show: true，ShardingSphere 会把逻辑 SQL 与实际执行的物理 SQL 都打进日志。上线前务必把核心接口的真实 SQL 都跑一遍，检查每个都能路由到单分片或可控的分片组。

示例二：游标分页 SQL 写法对比（消灭 OFFSET 深翻页）：

-- ❌ 深翻页：每次都要扫描并丢弃前 100000 行，越翻越慢
SELECT * FROM orders WHERE user_id = 888
ORDER BY create_time DESC LIMIT 20 OFFSET 100000;

-- ✅ 游标分页：用上一页末行 ID 作游标，任意页深度都是索引扫描
SELECT * FROM orders
WHERE user_id = 888 AND order_id < 1873456789012345678
ORDER BY order_id DESC LIMIT 20;
-- 客户端把本页最后一条的 order_id 作为下一页请求的 last_id 传回
