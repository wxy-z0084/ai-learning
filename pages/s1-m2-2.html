Few-shot 示例提示

预计 0.5 天模块二 · 提示词工程

一、学习目标

  • 能够解释 Zero-shot、One-shot、Few-shot 的区别及各自适用场景。
  • 能够为一个分类或改写任务挑选并组织 3~5 个高质量示例。
  • 能够识别「示例污染」问题：示例顺序、比例、格式不一致导致的输出偏差。
  • 能够用「示例 + 规则」组合的方式解决纯规则搞不定的模糊任务。

二、核心知识点

知识点 1：从 Zero-shot 到 Few-shot——示例是一种「隐性规则」

Zero-shot 不给示例，只靠指令；One-shot 给一个示例；Few-shot 通常给 2~8 个「输入 → 输出」配对。示例的本质是：当你无法用语言把规则描述清楚时，用实例把规则「演示」给模型。有些任务的规范极难言说——「什么算标题党」「什么算委婉的拒绝」「这条文本该归到哪个内部标签」——写成规则要几十条还漏边角，而给 5 个例子，模型立刻「心领神会」。Few-shot 同时还能锁定输出格式：示例用什么结构，模型就沿用什么结构，比抽象地写「请输出 JSON」有效得多。

选型经验：任务规则清晰、格式简单 → Zero-shot 足够，省 token；规则清晰但格式复杂 → 加 1 个示例锚定格式（One-shot）；规则模糊、类别边界靠感觉 → Few-shot，且每个可能的类别都要有示例覆盖。

知识点 2：示例的四个质量标准

①代表性：示例要覆盖任务的真实分布，包括边界与困难样本。只放简单正例，模型遇到绕弯的说法就会翻车。比如做「情感分类」，除了明显好评差评，一定要放一条阴阳怪气的（「真是太'棒'了，等了两个小时」）。②一致性：所有示例必须使用完全相同的格式、口吻与标注体系，包括标点和换行；不一致的示例会互相打架，模型随机学一个。③独立性：示例之间不能有信息泄漏（如示例 A 的答案里出现了示例 B 的内容），否则模型会「抄近路」。④顺序策略：示例顺序会影响权重，常见做法是把最典型、最完整的示例放在最后（离真实输入最近，影响力最大）；分类任务还要平衡各类别出现次数，别让某一类占了 4/5，模型会倾向多判那一类。

示例数量的边际效应：1→3 个提升明显，3→5 个继续提升，8 个以上收益趋缓而 token 成本线性上涨。生产环境建议从 3 个起步，用真实 bad case 驱动增补。

知识点 3：与规则混用及常见坑

Few-shot 不是万能药，最稳的组合是「规则定边界 + 示例定风格」：用上一节的四段式把硬规则写死（禁止编造、输出字段），再用示例演示边界情况的处理方式。例如工单分类：规则写清「标签清单与优先级定义」，示例演示「同时涉及退款和投诉时归到哪类」。常见坑有三个：示例里含有敏感或个人信息（示例会被拼进提示词，等于每次调用都外发一遍，务必脱敏）；示例与实时输入格式不匹配（示例输入是纯文本，真实输入带表格，模型会困惑）；示例过时（业务规则改了，示例还在按旧规则标注，输出新旧混杂——示例和规则要一起纳入版本管理，下节展开）。

三、示例演示

示例一：一个「客服工单意图分类 + 优先级判定」的 Few-shot 提示词，规则与示例配合使用，可直接粘贴使用：

# 角色与任务
你是电商客服系统的工单分诊员。读取用户工单文本，输出意图标签与优先级。

# 标签清单（规则）
意图 ∈ {退款申请, 物流投诉, 商品咨询, 技术故障, 其他}
优先级规则：涉及资金 > 涉及无法使用 > 一般咨询；同一工单取最高级。

# 示例
【输入】我昨天付的钱怎么还没到账？申请退款三天了
【输出】{"intent": "退款申请", "priority": "P1", "reason": "涉及资金且已超时"}

【输入】快递显示签收但我没收到，联系快递员也不回
【输出】{"intent": "物流投诉", "priority": "P2", "reason": "物品疑似丢失，非资金问题"}

【输入】你们 App 一打开就闪退，手机是 iPhone 15
【输出】{"intent": "技术故障", "priority": "P2", "reason": "用户完全无法使用产品"}

【输入】请问这个杯子可以进洗碗机吗
【输出】{"intent": "商品咨询", "priority": "P3", "reason": "一般性咨询，无紧急性"}

【输入】我要投诉你们客服，顺便问下怎么开发票
【输出】{"intent": "其他", "priority": "P2", "reason": "投诉情绪需安抚，同时含次要咨询，取较高级"}

# 输出要求
只输出一行 JSON，字段为 intent、priority、reason，reason 不超过 20 字。

注意第 5 个示例的作用：它演示了「一单多意图时如何取舍」——这种规则写三句话都说不清，一个示例就说明白了。这正是 Few-shot 的价值所在。

示例二：用 Python 组织示例列表，方便程序化维护与消融实验（去掉某个示例看准确率变化）：

EXAMPLES = [
    ("我昨天付的钱怎么还没到账？申请退款三天了",
     '{"intent": "退款申请", "priority": "P1"}'),
    ("快递显示签收但我没收到，联系快递员也不回",
     '{"intent": "物流投诉", "priority": "P2"}'),
    ("你们 App 一打开就闪退，手机是 iPhone 15",
     '{"intent": "技术故障", "priority": "P2"}'),
]

def build_prompt(ticket: str, examples=EXAMPLES) -> str:
    shots = "\n\n".join(
        f"【输入】{x}\n【输出】{y}" for x, y in examples
    )
    return f"# 分诊规则\n意图∈{{退款申请,物流投诉,技术故障,其他}}\n\n# 示例\n{shots}\n\n# 待处理\n【输入】{ticket}\n【输出】"

# 消融实验：逐个去掉示例，比较分类准确率，找出冗余示例
for i in range(len(EXAMPLES)):
    subset = EXAMPLES[:i] + EXAMPLES[i + 1:]
    print(f"去掉第 {i + 1} 个示例后评估……")
💡 提示：示例之间的分隔符要显式且统一（如「【输入】/【输出】」标签或三引号块），否则真实输入可能与示例边界混淆，模型会把你的新输入当成示例的一部分。最后一行永远留给真实输入。

四、实践任务

  1. 任务 1：挑一个分类任务（如垃圾邮件识别、评论打标），先用 Zero-shot 测 10 条样本记录准确率，再加 3 个示例重测，对比提升幅度。
  2. 任务 2：在任务 1 的示例集中加入 1 条「边界困难样本」，验证模型对该类样本的判断是否改善，并把这条示例保留进正式版本。
  3. 任务 3：故意把示例的输出格式改乱（两个示例用 JSON、一个用纯文本），观察输出稳定性变化，体会一致性的重要性。
  4. 任务 4（进阶，可选）：用上面的消融实验代码思想，做 3 个示例的两两组合测试，找出「性价比最高」的最小示例集。
