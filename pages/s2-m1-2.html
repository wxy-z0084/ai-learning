异步编程（asyncio）与并发处理

预计 1 天模块一 · Python 全栈

一、学习目标

  • 能够说清并发（Concurrency）与并行（Parallelism）的区别，判断一个任务该用 asyncio、线程还是进程。
  • 能够使用 async / await 定义协程，并用 asyncio.gather、create_task 并发调度多个 I/O 任务。
  • 能够识别并消除事件循环阻塞（同步耗时调用、CPU 密集计算），会用 to_thread / ProcessPoolExecutor 把阻塞工作移出事件循环。
  • 能够读懂 FastAPI 中异步路由的写法，理解为什么「全链路 async 才有收益」。

二、核心知识点

知识点 1：协程、事件循环与 async/await

协程（coroutine）是可以在执行中途挂起、让出控制权再恢复的函数，由 async def 定义，用 await 等待一个可等待对象（另一个协程、Future、Task）。所有协程都运行在事件循环（event loop）这一个线程上：遇到 await 的 I/O 就登记回调、去执行别的协程，I/O 完成后被唤醒继续。因此 asyncio 适合高并发 I/O（同时请求几百个接口、等模型推理返回），而不适合 CPU 密集计算——后者会独占循环，让所有协程一起卡住。

常见坑：await 只能写在 async def 里；同步函数里不能 await；一个未 await 的协程会产生「coroutine was never awaited」警告且什么也不执行。

知识点 2：并发调度：gather、create_task 与超时控制

asyncio.gather(*coros) 并发跑多个协程并按传入顺序收集结果，任一抛异常默认立即传播；asyncio.create_task(coro) 把协程包装成 Task 立刻调度，适合"先启动、稍后再取结果"的场景。asyncio.wait_for(coro, timeout=10) 给单个任务加超时，超时抛 TimeoutError；Python 3.11+ 还可用 asyncio.timeout() 上下文管理器统一罩住一段逻辑。批量调用大模型时，通常再用 Semaphore(n) 限制同时在途请求数，避免触发限流。

知识点 3：异步迭代、队列与异步上下文管理器

异步世界有成对的语法：async for 配合 __aiter__（如 httpx 流式响应、Redis pub/sub），async with 配合 __aenter__ / __aexit__（如 async with httpx.AsyncClient() as client）。asyncio.Queue 是生产者-消费者模型的核心：一个协程把任务 put 进队列，多个 worker 协程 get 出来并发处理，天然形成限速与削峰，实现并发批量推理时非常好用。

知识点 4：线程池与进程池——同步代码的出路

遇到无法改成异步的阻塞库（旧 SDK、同步数据库驱动、time.sleep），有三条路：用 asyncio.to_thread(fn, args)（3.9+）把调用丢进默认线程池；用 loop.run_in_executor(executor, fn) 指定自定义 ThreadPoolExecutor；CPU 密集任务则用 ProcessPoolExecutor 绕过 GIL 真正多核并行。原则：事件循环里只放 I/O 等待，重活一律外包。另外要记住线程不共享协程的上下文（contextvars 需要显式复制），线程间共享状态必须加锁。

三、示例演示

示例一：并发请求多个接口并统计总耗时——顺序执行 3 个 1 秒的请求要 3 秒，并发执行约 1 秒：

import asyncio
import httpx

async def fetch(client: httpx.AsyncClient, url: str) -> tuple[str, int]:
    resp = await client.get(url)
    return url, resp.status_code

async def main() -> None:
    urls = [
        "https://httpbin.org/delay/1",
        "https://httpbin.org/status/200",
        "https://httpbin.org/status/404",
    ]
    async with httpx.AsyncClient(timeout=10) as client:
        # gather 保序返回；return_exceptions=True 让单个失败不拖垮整体
        results = await asyncio.gather(
            *(fetch(client, u) for u in urls),
            return_exceptions=True,
        )
    for item in results:
        print(item)

asyncio.run(main())

示例二：用 Semaphore 限流 + Queue 生产者-消费者做批量任务，这是「批量喂给模型/接口」的标准骨架：

import asyncio

async def worker(name: str, sem: asyncio.Semaphore, queue: asyncio.Queue):
    while True:
        item = await queue.get()          # 队列空时挂起，不占 CPU
        if item is None:                  # 毒丸信号：通知退出
            queue.task_done()
            break
        async with sem:                   # 同时最多 size 个在途
            await asyncio.sleep(0.5)      # 模拟一次推理/请求
            print(f"{name} 处理完 {item}")
        queue.task_done()

async def main():
    queue: asyncio.Queue = asyncio.Queue(maxsize=100)
    sem = asyncio.Semaphore(5)
    workers = [asyncio.create_task(worker(f"w{i}", sem, queue))
               for i in range(8)]
    for i in range(30):
        await queue.put(i)
    await queue.join()                    # 等所有任务被消费完
    for _ in workers:
        await queue.put(None)
    await asyncio.gather(*workers)

asyncio.run(main())
💡 提示：调试 asyncio 出问题时先问三件事——有没有 await 漏了？事件循环里有没有混入阻塞调用（requests、time.sleep、同步 DB）？有没有用同一个 client/连接在多个协程间共享不当状态？

四、实践任务

  1. 任务 1：写脚本分别用「for 循环顺序 await」和「asyncio.gather 并发」请求同一个接口 10 次，用 time.perf_counter 打印两种方式的总耗时并对比。
  2. 任务 2：给任务 1 加上 asyncio.Semaphore(3) 限流与 asyncio.wait_for(..., timeout=5) 超时，验证限流生效、超时任务能被优雅处理（return_exceptions=True）。
  3. 任务 3：用 asyncio.Queue 实现一个 4 worker 的批量处理器，输入 100 个待处理项，其中混入会抛异常的项，保证单个失败不影响其余任务完成。
  4. 任务 4（进阶，可选）：写一个 CPU 密集函数（如大矩阵乘法），比较直接 await、asyncio.to_thread、ProcessPoolExecutor 三种方式的耗时，写下你观察到的原因。
