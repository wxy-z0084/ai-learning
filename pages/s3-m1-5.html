SpringBoot 自动配置与 Starter

预计 1 天模块一 · Java / SpringBoot

一、学习目标

  • 能够解释"约定优于配置"，说明 Spring Boot 自动配置如何在启动时替你装配 Bean。
  • 能够读懂自动配置类的注册与条件机制（@AutoConfiguration、@ConditionalOn*、@EnableConfigurationProperties）。
  • 能够独立开发一个自定义 Starter：配置属性类 + 自动配置类 + 注册文件 + 使用方引入。
  • 能够用日志或 /actuator/env 等手段排查"某个 Bean 为什么没生效/生效了"。

二、核心知识点

知识点 1：Spring Boot 为什么"开箱即用"

传统 Spring 项目要写大量 XML 或 @Configuration 来装配数据源、MVC、事务管理器。Spring Boot 的思路是约定优于配置：只要 classpath 上存在某个类或某项配置存在，就自动替你注册好对应的 Bean，开发者不写任何配置也能跑；想改默认行为，用 application.yml 或 @Bean 覆盖即可。入口的 @SpringBootApplication 实际是三个注解的组合：@SpringBootConfiguration（配置类）、@EnableAutoConfiguration（开启自动配置）、@ComponentScan（扫描本包及子包的组件）。

知识点 2：自动配置的执行机制

@EnableAutoConfiguration 通过 AutoConfiguration.imports（Spring Boot 3.x，旧版是 spring.factories）拿到全部候选自动配置类，然后逐个应用条件注解决定是否生效：@ConditionalOnClass（classpath 存在指定类）、@ConditionalOnMissingBean（容器里还没有该 Bean，这是"用户可覆盖默认"的关键）、@ConditionalOnProperty（配置项满足条件，可用 matchIfMissing 设默认值）、@ConditionalOnWebApplication。理解 @ConditionalOnMissingBean 就理解了"为什么我自己定义一个 Bean 就能覆盖 Boot 默认的"。排查工具：开启 debug=true 输出条件评估报告（Conditional evaluation report），或用 Actuator 的 /actuator/beans 查看 Bean 来源。

知识点 3：自定义 Starter 的标准结构

Starter 的本质是"依赖 + 自动配置"的打包约定，便于把公司内部组件（如限流器、统一鉴权、模型客户端）复用到多个服务。推荐拆两个模块：xxx-spring-boot-autoconfigure（放配置属性类与自动配置类）与 xxx-spring-boot-starter（只做依赖聚合，引入 autoconfigure 与必要的传递依赖）。开发三步：① 写 @ConfigurationProperties 配置属性类（前缀统一、字段有默认值）；② 写 @AutoConfiguration 类，用 @ConditionalOnMissingBean 注册组件；③ 在 META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports 中登记类全名。使用方只需引入 starter 依赖并按前缀配置即可生效。

三、示例演示

示例一：配置属性类与自动配置类（一个简单的限流组件 starter）：

// KbRateProperties.java
@ConfigurationProperties(prefix = "kb.rate")
public class KbRateProperties {
    /** 每秒允许的请求数，默认 5 */
    private double permitPerSecond = 10;
    /** 是否启用，默认 true */
    private boolean enabled = true;

    // 省略 getter / setter
}

// RateLimiterAutoConfiguration.java
@AutoConfiguration
@EnableConfigurationProperties(KbRateProperties.class)
@ConditionalOnProperty(prefix = "kb.rate", name = "enabled",
        havingValue = "true", matchIfMissing = true)
public class RateLimiterAutoConfiguration {

    @Bean
    @ConditionalOnMissingBean   // 用户自己定义 RateLimiter 时此处让位
    public RateLimiter rateLimiter(KbRateProperties props) {
        return new RateLimiter(props.getPermitPerSecond());
    }
}

示例二：注册文件与使用方配置——没有这两步，上面的类永远不会被加载：

# kb-rate-spring-boot-autoconfigure/src/main/resources/
#   META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports
com.example.ratelimit.RateLimiterAutoConfiguration

# 使用方 application.yml（starter 已在 classpath）
kb:
  rate:
    permit-per-second: 20
    enabled: true
💡 提示：写 Starter 时命名要带组织前缀（如 kb-rate）避免与生态冲突；配置属性类加 @Validated 可在启动期校验非法值；上线前用 debug=true 检查你的自动配置类是否出现在条件评估报告的 positive matches 中。

四、实践任务

  1. 任务 1：在现有项目中开启 debug=true，找到条件评估报告，指出 spring-boot-starter-web 触发了哪些自动配置类。
  2. 任务 2：自定义一个 Bean（如自定义 ObjectMapper），验证它如何覆盖 Boot 默认配置，并解释 @ConditionalOnMissingBean 的作用。
  3. 任务 3：按本节结构开发 kb-rate-spring-boot-starter（autoconfigure + starter 两模块），在另一个工程中引入并验证限流生效。
  4. 任务 4（进阶，可选）：为 starter 增加 @Validated 与校验注解（permitPerSecond 必须大于 0），填入非法值验证启动失败并给出可读的报错。
