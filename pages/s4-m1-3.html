API 网关（Gateway）与负载均衡

预计 1 天模块一 · 微服务架构

一、学习目标

  • 能够说清网关承担的六项职责（统一入口、路由、鉴权、限流、灰度、审计），并区分网关与普通反向代理。
  • 能够用断言（Predicate）+ 过滤器（Filter）写出 Spring Cloud Gateway 路由规则，解释路由匹配顺序。
  • 能够配置客户端负载均衡策略与超时重试，说明为何"重试叠加"会放大故障。
  • 能够给网关加上令牌校验与全链路 traceId 透传，并完成一次灰度发布实验。

二、核心知识点

知识点 1：为什么必须有网关

没有网关时，前端要维护 N 个服务地址，鉴权、限流、日志要在每个服务里重复实现，还无法统一做灰度与审计。API 网关是所有流量的唯一入口：外部请求先到网关，由它完成路由转发（按路径/主机头把 /api/order/** 转给 order-service）、统一鉴权（校验 JWT 后把用户信息注入请求头）、限流熔断（按接口或租户限流）、灰度分流（按 header/用户把 5% 流量导到新版本）、日志与审计（统一打印 traceId、耗时、响应码）。它与 Nginx 反向代理的区别在于：反向代理主要按域名/路径做四层七层转发，网关则是业务感知的——断言能读 Cookie、Header、参数，过滤器能改写请求与执行业务逻辑，且路由表可动态对接注册中心。代价是网关成了关键单点：必须集群部署、配置要跟上服务变更、并控制它自身的耗时预算（通常 < 10ms）。

知识点 2：Spring Cloud Gateway 的三件套

Spring Cloud Gateway 基于 WebFlux 响应式构建，路由定义由三部分组成：路由 ID、断言集合（匹配条件，任一命中即匹配：Path、Method、Header、Query、Cookie、After/Before 时间窗、Weight 权重）、过滤器链与目标地址（lb://服务名 表示交给负载均衡器解析）。多条路由按 order 从小到大依次尝试，因此带通配的兜底路由（如 Path=/**）必须排在最后，否则会把精确路由全部吃掉。常用内置过滤器：StripPrefix（去掉前缀）、AddRequestHeader（注入标识）、RewritePath（正则重写路径）、RequestRateLimiter（基于 Redis 的限流）、CircuitBreaker（接 Sentinel/Resilience4j 熔断降级）。常见坑：前端带 /api 前缀而服务没有——用 StripPrefix 统一裁剪；转发时丢失客户端真实 IP——用 AddRequestHeader=X-Forwarded-For 或 Forwarded 头过滤器补上。

知识点 3：客户端负载均衡的正确配置

Spring Cloud 用的是客户端负载均衡（Spring Cloud LoadBalancer）：调用方从注册中心拿到实例列表后，在本地按策略选择——默认轮询，可配置随机、权重（按实例流量比例，适合灰度）、一致性哈希（同用户落同实例，适合有本地缓存的场景）。配置时三个参数最影响稳定性：连接超时、读超时、重试次数。务必记住放大效应——网关重试 2 次 × 客户端重试 2 次 = 最坏 4 倍请求量，故障时重试会把雪崩从一个服务扩散到全链路，所以重试只对幂等 GET 开启、次数 ≤ 2，并配合熔断（下一节的 Sentinel）快速失败。

三、示例演示

示例一：网关的路由配置（application.yml）。注意精确路由在前、通配兜底在后，并演示 StripPrefix、超时与灰度权重：

server:
  port: 8080
spring:
  application:
    name: api-gateway
  cloud:
    nacos:
      discovery:
        server-addr: 127.0.0.1:8848
    gateway:
      httpclient:
        connect-timeout: 2000             # 网关→下游连接超时（毫秒）
        response-timeout: 5s              # 响应超时，防止下游慢请求拖死网关
      routes:
        - id: order-route
          uri: lb://order-service           # 走注册中心 + 客户端负载均衡
          predicates:
            - Path=/api/order/**            # 只匹配订单路径
            - Method=GET,POST
          filters:
            - StripPrefix=1                 # /api/order/list -> /order/list
            - AddRequestHeader=X-Gateway, edge-gateway
            - name: CircuitBreaker          # 熔断降级（接 Sentinel，见下一节）
              args:
                name: orderCB
                fallbackUri: forward:/fallback/order

        - id: gray-route
          uri: lb://order-service
          predicates:
            - Path=/api/order/**
            - Header=X-Gray-Tag, canary     # 带灰度标头的请求定向到新版本
          filters:
            - StripPrefix=1

        - id: default-fallback              # 兜底路由必须 order 最大
          uri: lb://order-service
          predicates:
            - Path=/**
          order: 100
      default-filters:
        - AddResponseHeader=X-Response-From, gw
    loadbalancer:                          # 客户端负载均衡重试：次数宁小勿大
      retry:
        enabled: true
        max-retries-on-next-service: 1     # 换下一个实例重试 1 次
        max-retries-on-same-service: 0     # 同一实例不重复打
        retry-on-all-exceptions: false     # 业务异常不要重试，否则放大故障

示例二：全局过滤器——统一校验令牌、透传用户身份与 traceId（缺失直接拒绝，不让无效流量进入内网）：

@Component
public class AuthGlobalFilter implements GlobalFilter, Ordered {

    private static final Set<String> WHITE = Set.of("/api/auth/login", "/fallback");

    @Override
    public Mono<Void> filter(ServerWebExchange ex, GatewayFilterChain chain) {
        String path = ex.getRequest().getURI().getPath();
        if (WHITE.contains(path)) {
            return chain.filter(ex);          // 白名单直接放行
        }

        String token = ex.getRequest().getHeaders().getFirst("Authorization");
        if (token == null || !verify(token)) { // 真实项目里校验 JWT 签名与过期时间
            ServerHttpResponse resp = ex.getResponse();
            resp.setStatusCode(HttpStatus.UNAUTHORIZED);
            resp.getHeaders().setContentType(MediaType.APPLICATION_JSON);
            String body = "{\"code\":401,\"msg\":\"invalid or missing token\"}";
            DataBuffer buf = resp.bufferFactory().wrap(body.getBytes(StandardCharsets.UTF_8));
            return resp.writeWith(Mono.just(buf));
        }

        // 把用户身份与链路追踪 ID 传给下游服务
        String traceId = MDC.get("traceId") != null ? MDC.get("traceId")
                                                    : UUID.randomUUID().toString().replace("-", "");
        ServerHttpRequest req = ex.getRequest().mutate()
                .header("X-User-Id", parseUserId(token))
                .header("X-Trace-Id", traceId)
                .build();
        return chain.filter(ex.mutate().request(req).build());
    }

    @Override
    public int getOrder() { return -100; }     // 数值越小越先执行
}
💡 验证路由是否命中的最快办法：在响应头看 X-Response-From，用 curl -H "X-Gray-Tag: canary" 打同一路径观察落点差异；上线前务必压测网关自身吞吐，它是全链路的天花板。

四、实践任务

  1. 任务 1：新建 gateway-service（WebFlux）接入 Nacos，配置两条路由把 /api/order/** 与 /api/pay/** 转发到对应服务，用 curl 验证 StripPrefix 后服务端收到的路径正确。
  2. 任务 2：实现示例二的鉴权过滤器：无 Token 返回 401 JSON，合法 Token 透传 X-User-Id 与 X-Trace-Id；在下游服务打印请求头确认透传成功。
  3. 任务 3：起 2 个 order-service 实例（不同端口注册同服务名），把其中 1 个改慢 3 秒，观察轮询下的超时表现；随后调整超时/重试参数，记录故障请求量的变化。
  4. 任务 4（进阶，可选）：用 Weight 断言或灰度标头把 10% 流量导到 v2 版本接口，验证比例符合预期，并设计一条回滚步骤（摘掉新实例即可恢复）。
