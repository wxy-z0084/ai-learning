MyBatis / JPA 数据访问

预计 1 天模块一 · Java / SpringBoot

一、学习目标

  • 能够解释 ORM 的基本思想，并说清 MyBatis（SQL 映射）与 JPA（对象关系映射）的定位差异与选型依据。
  • 能够编写 MyBatis 的 Mapper 接口与 XML，正确使用 #{} 与 ${} 并说明二者的安全含义。
  • 能够使用 JPA 的 CrudRepository/JpaRepository 与派生查询方法完成常见数据操作。
  • 能够识别并解决 N+1 查询问题，理解 @Transactional 事务边界与失效场景。

二、核心知识点

知识点 1：两种数据访问范式

MyBatis 是 SQL 映射框架：Java 方法与 SQL 语句一一对应，SQL 完全可控，复杂查询、多表关联、报表统计写起来顺手，是国内大量存量系统的标配；代价是 SQL 样板代码多、对象与表的映射要手工维护。JPA（Hibernate 实现） 是 ORM：实体类映射表、属性映射列，通过 Repository 方法名或 @Query 操作对象，自带一级缓存、脏检查与懒加载，CRUD 与简单查询代码量极小；代价是 SQL 隐藏在框架后，优化复杂查询需要看懂生成的 SQL。选型经验：CRUD 多、模型稳定选 JPA；报表与复杂 SQL 多选 MyBatis，二者也可在一个项目中共存（JPA 管主流程，MyBatis 管复杂查询）。

知识点 2：MyBatis 的安全与映射要点

核心规则：#{} 是预编译占位符（PreparedStatement 的 ?），参数以传值方式绑定，天然防注入；${} 是字符串直接拼接，会带来 SQL 注入风险，只允许用于排序字段、表名等"不能参数化的位置"，且必须用白名单校验。常见坑：LIKE 模糊查询要用 CONCAT('%', #{kw}, '%') 或绑定前后缀，而不是 ${kw}；返回 resultMap 用于列名与属性不一致或一对多映射；用 useGeneratedKeys 回填自增主键。

知识点 3：JPA 的懒加载、N+1 与事务

JPA 实体间的一对多、多对一关联默认懒加载——首次访问时才发 SQL。便利的背后是经典性能陷阱 N+1 问题：先查出 10 个 Ticket，遍历时每个 Ticket 再查一次关联的 User，1 次查询变 11 次。解决办法：用 @EntityGraph 或 fetch join 一次性关联取出，或改用投影 DTO。@Transactional 默认只对 RuntimeException 回滚，边界应放在 Service 层且"一次业务操作一个事务"；注意事务内不要做远程调用（拉长数据库连接持有时间），自调用不走代理也会导致事务失效。

三、示例演示

示例一：MyBatis Mapper 接口与 XML（注意 #{} 与安全的 LIKE 写法）：

// TicketMapper.java
@Mapper
public interface TicketMapper {
    List<Ticket> search(@Param("status") String status,
                        @Param("keyword") String keyword,
                        @Param("offset") int offset,
                        @Param("limit") int limit);

    int insert(Ticket ticket);   // useGeneratedKeys 回填 id
}

<!-- resources/mapper/TicketMapper.xml -->
<select id="search" resultType="com.example.domain.Ticket">
    SELECT id, title, status, created_at
    FROM ticket
    WHERE status = #{status}
      AND title LIKE CONCAT('%', #{keyword}, '%')  <!-- 禁止写成 ${keyword} -->
    ORDER BY id DESC
    LIMIT #{offset}, #{limit}
</select>

<insert id="insert" useGeneratedKeys="true" keyProperty="id">
    INSERT INTO ticket (title, description, status)
    VALUES (#{title}, #{description}, #{status})
</insert>

示例二：JPA Repository、避免 N+1 的查询与事务边界：

public interface TicketRepository extends JpaRepository<Ticket, Long> {

    // 派生查询：方法名即查询条件
    List<Ticket> findByStatusOrderByCreatedAtDesc(TicketStatus status);

    // EntityGraph 一次性取出关联的提交人，避免 N+1
    @EntityGraph(attributePaths = "creator")
    List<Ticket> findTop20ByStatus(TicketStatus status);
}

@Service
public class TicketService {
    private final TicketRepository repository;

    public TicketService(TicketRepository repository) {
        this.repository = repository;
    }

    @Transactional
    public Ticket close(long id, String operator) {
        Ticket ticket = repository.findById(id)
                .orElseThrow(() -> new IllegalArgumentException("工单不存在"));
        ticket.setStatus(TicketStatus.CLOSED);   // 脏检查自动更新，无需显式 save
        return ticket;
    }
}
💡 提示：开启 spring.jpa.show-sql=true 与 Hibernate 的 SQL 格式化输出（或用 P6Spy），写完查询先看真实 SQL 再提交；N+1 一旦上线才发现，慢查询会随数据量放大。
