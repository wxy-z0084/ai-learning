JVM 调优与 SQL 优化

预计 1 天模块五 · 高并发系统落地

一、学习目标

  • 能够读懂 GC 日志与内存快照，区分"分配过快"和"泄漏"两类问题，并用正确参数治理 Full GC。
  • 能够用 EXPLAIN 分析执行计划，识别全表扫描、临时表、文件排序等危险信号并改写 SQL。
  • 能够制定"先测后调"的调优流程：以压测数据为依据，每次只改一个变量，改完复测。

二、核心知识点

知识点 1：调优的正确姿势——别上来就改参数

绝大多数"卡顿"不是因为 JVM 参数不好，而是代码写得差：循环里 new 大对象、无界缓存、流没关闭、日志里拼接超大 JSON。正确的顺序是：先用工具确认问题位置，改代码能解决就绝不碰参数。JDK 17+ 默认的 G1 收集器在大多数场景已经够用，盲目换成 ZGC 或 Shenandoah 只会让问题更难排查。

三个核心观察量：吞吐量（业务时间占比）、暂停时间（Stop-The-World 时长，直接影响用户可感延迟）、堆占用曲线形状（锯齿正常，水平线不回落=泄漏，陡坡式上升=分配过快）。

知识点 2：JVM 问题定位的工具链

轻量级先上 jstat（看各区占用与 GC 次数频率）、jmap -histo（看对象数量排行榜，几十万个 byte[] 基本就是缓存没设上限）。抓 jmap -dump 堆快照后用 Eclipse MAT 或 VisualVM 分析支配树，找到被谁引用着（GC Root 路径）。JDK Mission Control（JMC）是官方利器，其 JFR（飞行记录器）开销低于 1%，可以长期挂在生产环境录制，出问题回放分析，比抓 dump 友好得多。

常见坑：堆设得越大越好是错的——堆越大 GC 扫描越慢、暂停越久；堆大小一般设为可用内存的 1/4 且不超过 32GB（开启指针压缩的上限）。另一个坑：-Xmx 和 -Xms 不一致会导致运行中动态扩容引发暂停。

知识点 3：SQL 优化的四大抓手

①索引：最左前缀原则、避免在索引列上做函数或隐式转换（WHERE DATE(create_time)=... 会让索引失效，改写成范围查询）；②避免 SELECT *：只取需要的列，大字段（text/json）尤其要避开；③分页优化：深分页 LIMIT 100000,10 会先扫描十万行再丢弃，改用"延迟关联"或记录上次最大 ID；④JOIN 与子查询：驱动表选择小表，子查询在数据量大时改写为 JOIN。

任何 SQL 优化的依据都只有两个：EXPLAIN 的执行计划和慢查询日志的真实耗时。"我觉得这个查询很慢"不算证据。

三、示例演示

示例一：开箱即用的生产级 JVM 启动参数（JDK 17 + G1，含 GC 日志），可直接替换默认值使用：

java -Xms4g -Xmx4g \                  # 堆初始值=最大值，避免运行时扩容抖动
      -XX:+UseG1GC \
      -XX:MaxGCPauseMillis=200 \       # 目标暂停时间（业务可接受的延迟上限）
      -XX:G1HeapRegionSize=8m \
      -XX:+HeapDumpOnOutOfMemoryError \
      -XX:HeapDumpPath=/data/logs/heap.hprof \
      -Xlog:gc*:file=/data/logs/gc.log:time,uptime,level,tags:filecount=5,filesize=20m \
      -jar order-service.jar

示例二：深分页优化——把扫描 10 万行的 LIMIT 改写为延迟关联：

-- ❌ 低效：MySQL 需要扫描并丢弃前 100000 行
SELECT id, title, amount FROM orders ORDER BY id LIMIT 100000, 10;

-- ✅ 优化：先用覆盖索引取 10 个 id，再回表取完整字段
SELECT o.id, o.title, o.amount
FROM orders o
JOIN (SELECT id FROM orders ORDER BY id LIMIT 100000, 10) t ON o.id = t.id;

-- 两者用 EXPLAIN 验证：后者 Extra 列不再出现 Using filesort，扫描行数骤降
EXPLAIN SELECT o.id, o.title, o.amount
FROM orders o JOIN (SELECT id FROM orders ORDER BY id LIMIT 100000, 10) t ON o.id = t.id;
💡 提示：JFR 录制一条命令就能开——jcmd <pid> JFR.start duration=10m filename=rec.jfr，然后用 JMC 打开可视化分析。生产环境想做"事后取证"，把它加到巡检脚本里就行。

四、实践任务

  1. 任务 1：给本地 Java 程序加上含 GC 日志的启动参数，跑一个压测场景，从 gc.log 里找出 Minor GC 与 Full GC 的频率和暂停时长。
  2. 任务 2：用 jmap -histo 统计一个运行中 Java 进程的对象 Top10，写 200 字分析哪个对象数量异常及可能原因。
  3. 任务 3：用 EXPLAIN 分析 5 条你项目里的真实 SQL，找出其中 2 条有优化空间的并改写，对比执行计划与耗时。
  4. 任务 4（进阶，可选）：用 JMC 录制 10 分钟 JFR 并回放，找出其中耗时最长的 3 个方法并提出优化思路。

五、推荐资源

  • 📖 OpenJDK Mission Control（JMC） — 官方低开销监控与 JFR 分析工具，本节推荐的首选工具
  • 📖 Java SE 17 Garbage Collection Tuning Guide — Oracle 官方 GC 调优手册，参数含义以它为准
  • 📖 JDK 官方 jcmd 命令手册 — jcmd/jstat/jmap 等自带诊断命令的权威参数说明，排查线上问题随查随用
  • 📖 MySQL 官方 EXPLAIN 文档 — 执行计划每个字段的权威解释，看懂 type/key/rows 三列就入门了
  • 📖 Use The Index, Luke — 数据库索引与 SQL 优化的经典免费电子书，示例覆盖主流数据库

六、自检清单

  • 我能通过堆占用曲线的形状区分"泄漏"和"分配过快"吗？
  • 我是否坚持"先用数据定位、改完复测"而不是凭感觉调参？
  • 我能独立写出一条含 GC 日志的生产级启动参数吗？
  • 面对一条慢 SQL，我能在 10 分钟内用 EXPLAIN 指出它慢在哪一步吗？
