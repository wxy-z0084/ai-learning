分布式事务（Seata、最终一致性）

预计 1 天模块二 · 分布式方案

一、学习目标

  • 能够说清单机事务与分布式事务的差异，用 CAP / BASE 理论解释为什么分布式场景大多追求"最终一致"。
  • 能够基于 Seata 完成一个跨服务转账示例：搭建 TC 服务端、在客户端加 @GlobalTransactional、建好 undo_log 表并验证回滚。
  • 能够设计一套本地消息表 + 定时重试的最终一致性方案，并说明幂等消费、补偿、对账三个兜底手段。
  • 能够根据业务场景在 AT、TCC、Saga、XA 之间做出合理选型，并指出各自的代价。

二、核心知识点

知识点 1：为什么需要分布式事务

传统单体应用里，一个数据库连接内的多个 SQL 可以靠 ACID 事务整体提交或回滚。但服务拆分后，订单库、库存库、账户库往往分属不同实例甚至不同机房，数据库层面的事务无法跨越多个数据源，于是"下单成功但扣款失败"这类不一致就出现了。

分布式系统受 CAP 定理约束：网络分区不可避免时，只能在一致性（C）和可用性（A）间取舍。多数业务互联网系统选择 AP + BASE 理论（基本可用、软状态、最终一致）：允许短时间不一致，但必须给出最终对齐的机制（重试、补偿、对账）。设计时先问自己：这个不一致窗口业务能不能容忍？不能容忍才考虑强一致方案（Seata AT/TCC/XA），能容忍就优先最终一致（本地消息表、事务消息），因为后者的吞吐和复杂度都低得多。

知识点 2：Seata 的四种模式

Seata（Simple Extensible Autonomous Transaction Architecture）是开源分布式事务框架，由 TC（事务协调器，独立部署）、TM（事务管理器，发起方）、RM（资源管理器，管理分支事务）三大组件构成。最常用的 AT 模式是无侵入的两阶段提交：一阶段业务 SQL 与"回滚日志"（undo_log）一起提交；二阶段若提交则异步清理日志，若回滚则用 undo_log 反向补偿。AT 的代价是全局锁——事务期间同一行数据的并发写会被串行化，高并发热点场景会明显拖慢写入。

TCC 模式要求业务实现 Try（预留资源）、Confirm（确认）、Cancel（撤销）三个接口，资源预留期内其他事务无法占用，性能最好但侵入性最强，适合库存扣减、账户冻结类场景。Saga 模式为每个长事务定义正向操作与补偿操作，适合流程长、无资源预留需求的业务（如履约审批流）。XA 模式依赖数据库的 XA 协议做强一致两阶段提交，隔离性最好但锁持有时间长，吞吐最低，一般只用于金融核心库对接。

常见坑：AT 模式下大事务（一次更新几千行）会拖垮 undo_log 表与全局锁；自增主键、唯一索引冲突在回滚时可能报"脏数据"；Seata 要求业务表必须有主键，且不支持部分 SQL（如 SELECT ... FOR UPDATE 需要单独评估）。

知识点 3：最终一致性的通用套路

不引入 Seata 也能解决 80% 的跨服务一致性问题，核心是把"同时成功"变成"先本地成功，再异步送达"。经典做法是本地消息表：业务写库与消息写入同一个本地事务，后台定时任务扫描"待发送"消息投递到 MQ，消费方处理成功后回写状态；配合唯一业务单号做幂等（消费端去重表或 Redis SETNX），失败则按指数退避重试，重试超限转人工，并定期用对账任务比对两边数据。RocketMQ 的事务消息（半消息机制）是该模式的托管版，省掉自己写扫描任务。

无论选哪种方案，三个兜底不可少：幂等（消息可能重复）、补偿（有正向就得有反向操作）、对账（任何机制都可能漏，T+1 对账是最后防线）。监控上要给"消息积压数、重试次数、事务回滚数"打点告警。

三、示例演示

示例一：Seata AT 模式的 Java 客户端关键代码。订单服务创建订单时同时调用账户服务扣款，任一环节异常则全局回滚。

// 订单服务：加入全局事务注解即可，无需写回滚逻辑
@Service
public class OrderService {

    @Autowired
    private OrderMapper orderMapper;
    @Autowired
    private AccountClient accountClient; // Feign 调用账户服务

    @GlobalTransactional(name = "create-order", rollbackFor = Exception.class)
    public void createOrder(Long userId, Long productId, BigDecimal amount) {
        orderMapper.insert(new Order(userId, productId, amount, "CREATED"));
        // 若这里抛异常，Seata 会回滚订单表的一阶段提交
        accountClient.deduct(userId, amount);
    }
}

每个接入 Seata 的数据库都要建回滚日志表（以 MySQL 为例），并配置数据源为 Seata 的代理数据源：

CREATE TABLE `undo_log` (
  `branch_id`     BIGINT       NOT NULL COMMENT 'branch transaction id',
  `xid`           VARCHAR(128) NOT NULL COMMENT 'global transaction id',
  `context`       VARCHAR(128) NOT NULL COMMENT 'undo_log context, such as serialization',
  `rollback_info` LONGBLOB     NOT NULL COMMENT 'rollback info',
  `log_status`    INT(11)      NOT NULL COMMENT '0: normal, 1: defense',
  `log_created`   DATETIME(6)  NOT NULL COMMENT 'create datetime',
  `log_modified`  DATETIME(6)  NOT NULL COMMENT 'modify datetime',
  UNIQUE KEY `ux_undo_log` (`xid`, `branch_id`)
) ENGINE = InnoDB COMMENT = 'AT transaction undo log';
💡 本地跑示例最快的方式是用 Seata 官方仓库里的 docker-compose 一键启动 TC（seata-server，默认 8091 端口），客户端配置 registry.conf / application.yml 指向它即可；数据库的 undo_log 表漏建是一阶段直接报错的最常见原因。

示例二：不用框架的本地消息表方案——订单库同事务写消息，定时任务投递并做幂等消费（Python 伪生产代码，SQL 换成你的 ORM 即可）：

import time, json, requests

def create_order_with_message(order_id, user_id, amount):
    with db.transaction():  # 同一个本地事务
        db.execute("INSERT INTO orders(id,user_id,amount,status) VALUES (%s,%s,%s,'CREATED')",
                   (order_id, user_id, amount))
        db.execute("INSERT INTO outbox_msg(id,biz_id,type,payload,status) VALUES (%s,%s,'DEDUCT',%s,'PENDING')",
                   (order_id, order_id, json.dumps({"userId": user_id, "amount": str(amount)})))

def pump_outbox():
    rows = db.query("SELECT id,payload FROM outbox_msg WHERE status='PENDING' ORDER BY id LIMIT 50")
    for row in rows:
        try:
            r = requests.post("http://account-service/deduct", json=json.loads(row.payload), timeout=2)
            if r.status_code == 200:  # 消费端按 biz_id 去重，重复投递无副作用
                db.execute("UPDATE outbox_msg SET status='SENT' WHERE id=%s", (row.id,))
        except Exception:
            time.sleep(1)  # 失败留待下一轮；可加 retry_count 字段做分级告警

  1. 任务 1：按 Seata 官方快速开始启动 seata-server + MySQL，写一个两服务（订单/账户）示例，在账户服务里人为抛异常，用日志与 undo_log 表验证全局回滚生效。
