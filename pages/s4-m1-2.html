注册中心与配置中心（Nacos）

预计 1 天模块一 · 微服务架构

一、学习目标

  • 能够解释服务注册与发现的完整流程：实例上线注册、心跳续约、下线摘除、客户端拉取地址列表。
  • 能够说清配置中心解决的四个问题（集中管理、动态刷新、多环境隔离、变更审计），并解释namespace / group / dataId 三级模型。
  • 能够完成 Nacos 单机部署，并让两个 Spring Cloud Alibaba 服务完成注册发现与配置拉取。
  • 能够排查注册与配置的高频故障：不注册、不刷新、namespace 配错、容器内 IP 注册错误。

二、核心知识点

知识点 1：注册中心——服务地址的"通讯录"

服务实例的 IP 与端口是动态的（扩缩容、发布换机），调用方不可能写死地址。解决办法是注册中心：实例启动时把 服务名 → IP:端口 注册进去，运行期间按间隔发送心跳续约，连续心跳失败则被判定不健康并摘除；调用方（如 LoadBalancer / OpenFeign）按服务名从注册中心拉取实例列表，在本地做负载均衡。Nacos 的实例分两类：临时实例（默认，走客户端心跳，心跳超时被踢出）与永久实例（由服务端主动探测，适合不宜自报心跳的中间件）。Nacos 采用 AP 为主、CP 为辅的模式：临时实例走 distro 协议保证可用性（AP），持久实例与配置数据走 Raft 强一致（CP）。常见坑：容器/Pod 内注册了内网网卡 IP 导致调用方连不上（要配 spring.cloud.nacos.discovery.ip 或使用 host 网络）；机器休眠导致心跳中断，本地开发时实例被误判下线。

知识点 2：配置中心——一次改、处处生效

把 application.yml 拆散在每个仓库里，改一个超时参数要发版十几个服务。配置中心把配置集中存储并支持运行时推送，配合多环境隔离（dev / test / prod 各一套命名空间）与变更历史回滚，是微服务治理的基础设施。Nacos 配置的定位规则是三级：namespace（隔离环境，如 dev/prod，最外层）、group（隔离业务线或应用组，如 DEFAULT_GROUP、trade）、dataId（单个配置文件，如 order-service.yaml）。Nacos 还会在服务启动时做共享配置导入（shared-configs / extension-configs），公共配置（Redis、日志级别）放共享文件，应用私有配置放自己的 dataId，加载优先级：应用配置 > 扩展配置 > 共享配置。另一个容易忽略的能力是 fail-fast 校验：配置文件不存在或格式错误时启动直接失败，配合 CI 校验能在发布前拦住手误。

知识点 3：动态刷新的正确姿势

在 Nacos 控制台改配置只是第一步，服务进程必须感知变更才能生效：Spring Cloud Alibaba 通过监听配置变更推送刷新，但刷新只对标注了 @RefreshScope 的 Bean（或配合 @ConfigurationProperties 绑定）生效。典型错误有三种：只加了 nacos-config 依赖却没写 spring.config.import 或 shared-configs，配置根本没拉下来；Bean 没加 @RefreshScope，@Value 字段值不更新；读取的 dataId 与控制台编辑的不一致（环境/profile 后缀没对上），改了却"看起来没生效"。验证手段：调用 /actuator/refresh 或直接观察变更日志，并在接口里回显配置值确认。

三、示例演示

示例一：order-service 同时接入服务注册与配置中心的 application.yml（Spring Cloud Alibaba 2022.x + Nacos 2.x 默认端口 8848）：

server:
  port: 8081
spring:
  application:
    name: order-service            # 注册到 Nacos 的服务名，调用方按它寻址
  cloud:
    nacos:
      discovery:
        server-addr: 127.0.0.1:8848
        namespace: dev-ns-id       # 控制台"命名空间"页面复制的 ID，不是名字！
        group: DEFAULT_GROUP
        ip: 192.168.1.50           # 容器内注册错 IP 时手动指定
        weight: 1.0
      config:
        server-addr: 127.0.0.1:8848
        namespace: dev-ns-id
        group: DEFAULT_GROUP
        file-extension: yaml        # 对应 dataId = order-service.yaml
        shared-configs:             # 公共配置（如 common-redis.yaml）
          - data-id: common-redis.yaml
            group: SHARED_GROUP
            refresh: true           # 必须为 true 才会随变更刷新

# 开发环境想禁用注册/配置时：spring.cloud.nacos.discovery.enabled=false

示例二：读取配置并支持动态刷新的业务 Bean——控制台把 order.limit 从 50 改成 100 后，无需重启即生效：

@RestController
@RequestMapping("/order")
@RefreshScope                       // 关键：缺了它 @Value 不会随配置更新
public class OrderController {

    @Value("${order.limit:10}")      // 带默认值，配置缺失也能启动
    private int limit;

    @Value("${order.timeout-ms:3000}")
    private long timeoutMs;

    @GetMapping("/limit")
    public Map<String, Object> limit() {
        // 用这个接口回显验证刷新是否生效
        return Map.of("limit", limit, "timeoutMs", timeoutMs,
                      "instance", "order-service");
    }

    @PostMapping
    public String create(@RequestBody OrderDTO dto) {
        if (dto.getCount() > limit) {
            throw new IllegalArgumentException("单次下单超过限额 " + limit);
        }
        return orderService.create(dto);   // 超时参数同样读自配置中心
    }
}
💡 先按官方快速开始用 docker 起单机 Nacos（docker run -e MODE=standalone -p 8848:8848 nacos/nacos-server:v2.3.2），控制台默认 nacos/nacos；上线前把配置的 fail-fast 打开，配置缺失宁可启动失败也不要带病上线。

四、实践任务

  1. 任务 1：按官方快速开始部署单机 Nacos，在控制台创建 dev/test 两个命名空间，创建 order-service.yaml 与共享配置 common-log.yaml 并观察 dataId、group 层级关系。
  2. 任务 2：创建两个 Spring Boot 服务（order-service、payment-service）接入注册中心，A 通过服务名调用 B；随后手动下线 B，验证 A 感知到实例摘除并报错/重试。
  3. 任务 3：实现示例二的动态刷新接口，把 order.limit 改 3 次，确认每次不重启即生效；再故意去掉 @RefreshScope 复现"改了不生效"并修复。
  4. 任务 4（进阶，可选）：模拟注册中心宕机（停掉 Nacos）观察客户端行为，配置本地快照缓存，并把 Nacos 部署为集群（2 节点）验证故障转移。
