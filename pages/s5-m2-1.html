微调场景判断（何时微调 vs RAG）

预计 0.5 天模块二 · LoRA 微调

一、学习目标

  • 能够说清微调与 RAG 的本质区别：一个改"怎么说话"，一个供"说什么"。
  • 能够按六个判断维度为具体场景在微调、RAG、二者结合之间做出有依据的选择。
  • 能够识别"该用 RAG 却去微调"的典型错误，并给出纠正方案。
  • 能够列出微调开工前的前置检查清单，避免在数据不足时盲目启动。

二、核心知识点

知识点 1：微调改变什么、不改变什么

微调是用业务数据更新模型权重，让模型把任务的"套路"内化：稳定的输出格式、行业术语的正确用法、特定的语气与详略偏好、对某类输入的判别倾向。它不擅长注入可查询的事实——你很难靠微调让模型记住一份会季度更新的价格表，即使记住了也无法给出出处、容易张冠李戴（表现为自信地编造）。与之相对，RAG 把知识放在模型外面：每次作答先检索相关片段，知识更新只需重建索引，答案可附引用链接、可审计，非常适合"知识量大、频繁更新、必须溯源"的场景。一句话记住：知识进 RAG，行为进微调；如果既能微调又能 RAG，通常也是各管一摊而不是二选一。

知识点 2：六维判断

① 知识更新频率：每周都变 → RAG；半年不变的领域惯例 → 微调。② 是否需要引用出处：需要（法务、医疗、客服话术合规）→ RAG。③ 问题类型：开放事实问答 → RAG；固定格式的判别与生成（分类、抽取、结构化改写、风格翻译）→ 微调。④ 数据量：有几百到上万条高质量"输入→期望输出"样本 → 微调有条件；只有文档没有标注对 → 老老实实 RAG。⑤ 成本与延迟：提示词里塞长文档导致 token 贵、延迟高，可微调 + 少量检索——让模型学会"给这点上下文就够用"。⑥ 隐私与私有化：数据不能出内网 → 微调出一个本地小模型，比自建大模型推理 + 全量知识库更省资源。

知识点 3：前置检查与组合范式

启动微调前问四个问题：基线达标了吗？——先把提示词 + few-shot 调到极致，微调必须对着这个基线比，否则无法证明自己的价值；样本够吗？——分类/抽取类通常几百条就有收益，风格与复杂推理建议千条以上，且质量远比数量重要（宁要 500 条精品，不要 5 万条噪声）；评测集准备好了吗？——训练/验证/测试必须分离，防止"练过题"的假高分；退化风险评估了吗？——微调会损失通用能力（灾难性遗忘），只在目标任务上变强，要保留通用问答的场景需混入通用数据。推荐的终局形态是"微调打底 + RAG 供知识 + 提示词兜底"：微调保证格式与语感稳定，RAG 保证事实准确可溯源。

三、示例演示

示例一：把六维判断固化成选型配置，评审时逐项打勾，结论一目了然：

# finetune-or-rag.yaml —— 三个场景的选型结论
scenarios:
  - name: 合同风险条款问答
    facts_change_often: true        # 条款库每月更新
    needs_citation: true            # 必须给出条款原文出处
    task_type: 事实问答
    data_pairs: 0                   # 只有文档，无标注对
    conclusion: RAG
    note: 微调无法提供出处，且知识更新会导致模型记忆过期

  - name: 工单分类与固定格式摘要
    facts_change_often: false
    needs_citation: false
    task_type: 判别与结构化生成
    data_pairs: 3000                # 历史已标注工单
    conclusion: 微调（LoRA）
    note: 纯提示词基线 82% → 目标 92%；格式稳定后可换更小模型，降本 80%

  - name: 产品手册导购问答
    facts_change_often: true
    needs_citation: true
    task_type: 事实问答 + 回答语气要求高
    data_pairs: 800                 # 优质客服对话对
    conclusion: RAG + 微调
    note: RAG 供事实与引用，微调学习品牌语气与拒答边界

示例二：一个可复用的判断函数，团队拿它当决策起点（结论仍需人工复核）：

def decide(ans: dict) -> str:
    """ans: 每项为 True/False 与数量的自评结果"""
    if ans["needs_citation"] or ans["knowledge_updates_often"]:
        # 会变、要溯源 → 检索打底
        return "RAG + 微调" if ans["data_pairs"] >= 500 else "RAG"
    if ans["data_pairs"] < 200:
        return "提示词工程（数据不足，先攒数据）"
    if ans["prompt_baseline_hit_target"]:
        return "提示词工程（已达标，勿微调）"
    return "微调（LoRA）"   # 行为/格式问题 + 数据充足 + 基线未达标

if __name__ == "__main__":
    ans = {"needs_citation": False, "knowledge_updates_often": False,
           "data_pairs": 3000, "prompt_baseline_hit_target": False}
    print("选型结论：", decide(ans))   # → 微调（LoRA）
💡 判断的黄金顺序：提示词 → RAG → 微调，逐级加码且不跳级。每上一级都要回答"上一级为什么不奏效"，并留下基线数字作为证据。

四、实践任务

  1. 任务 1：列出你手头 3 个 AI 候选场景，按示例一逐项填写六个判断维度，给出 RAG / 微调 / 组合 / 仅提示词的结论与理由。
  2. 任务 2：为结论是"微调"的场景做基线实验：纯提示词 + 3 个示例跑评测集，记录准确率，写明"微调要从多少提到多少"。
  3. 任务 3：盘点数据：能凑出多少条"输入→期望输出"样本？抽 20 条检查质量（答案是否一致、有无错标），写出数据补齐计划。
  4. 任务 4（进阶，可选）：为"RAG + 微调"组合场景画职责分工图：哪些信息走检索、哪些行为靠微调、提示词里还保留什么兜底规则。
