缓存（Redis）、任务调度（Quartz）

预计 1 天模块二 · 企业级单体项目开发

一、学习目标

  • 学完本节后，你能够判断哪些数据适合进缓存，并说出本地缓存与 Redis 分布式缓存的适用场景。
  • 你能够使用 Spring Cache 注解（@Cacheable / @CacheEvict）为查询接口加缓存，并解释其失效与序列化配置。
  • 你能够针对缓存穿透、击穿、雪崩三类问题给出具体的防护方案。
  • 你能够用 Quartz 配置定时任务，并说明单机 @Scheduled 与集群 Quartz 的选型区别。

二、核心知识点

知识点 1：Redis 缓存使用与 Spring Cache 抽象

缓存用于让读多写少、计算昂贵或远端的数据靠近应用：热点商品详情、字典表、配置项、频繁聚合的统计结果。选型上，单机且允许短暂不一致可用 Caffeine 等本地缓存；多实例部署必须用 Redis 这类分布式缓存，否则每个实例各存一份，内存翻倍且互相不一致。

Spring 提供了缓存抽象：@Cacheable（命中则不执行方法）、@CachePut（总是执行并更新缓存）、@CacheEvict（删除缓存），配合 CacheManager + RedisTemplate 即可无侵入接入。但要注意几个坑：同类内部方法互调不走代理，注解不生效；默认 JDK 序列化产生乱码，通常改为 JSON 的 GenericJackson2JsonRedisSerializer；@Cacheable 的 key 要包含关键入参（SpEL 如 #id），否则不同参数互相覆盖。

知识点 2：穿透、击穿、雪崩与一致性

穿透指查询一个一定不存在的数据，请求绕过缓存直达数据库：对策是缓存空值（短 TTL）或用布隆过滤器前置拦截。击穿指某个热 key 过期瞬间大量并发打库：对策是互斥锁重建（只允许一个线程回源）或逻辑过期（不设物理 TTL，value 里带过期时间，过期后异步刷新）。雪崩指大量 key 同时失效：给 TTL 加随机抖动、多级缓存、限流兜底。缓存与数据库一致性一般采用先更新数据库、再删除缓存，写多读少时可加"延迟双删"或订阅 binlog（如 Canal）异步失效。Redis 本身要规划好内存淘汰策略（常用 allkeys-lru）与 key 命名规范（业务:模块:id），警惕大 key 与慢查询。

知识点 3：任务调度 Quartz 与集群防重

定时任务分两档：简单的周期任务用 Spring 的 @Scheduled（cron 表达式）即可，但它是单机执行，多实例部署时会重复跑；需要可视化管理、动态调整触发时间、集群高可用时用 Quartz。Quartz 的核心概念是 Job（任务做什么）、JobDetail（任务定义）、Trigger（何时触发，SimpleTrigger 或 CronTrigger）、Scheduler（调度器）。Quartz 集群模式把触发器信息存到数据库（提供 MySQL 建表脚本），通过数据库行锁保证同一时刻只有一个实例执行同一个任务。任务内部要遵守"幂等"原则：无论重复执行几次结果一致，用唯一业务键 + 状态判断兜底。

三、示例演示

示例一：Spring Boot 整合 Redis + Spring Cache，application.yml 配置与带缓存的查询服务：

spring:
  data:
    redis:
      host: 127.0.0.1
      port: 6379
      timeout: 2s
      lettuce:
        pool: {max-active: 16, max-idle: 8, min-idle: 2}
  cache:
    type: redis
    redis:
      time-to-live: 10m   # 默认过期 10 分钟，可按注解单独指定

// 开启缓存
@SpringBootApplication
@EnableCaching
public class MallApplication { }

@Service
@RequiredArgsConstructor
public class GoodsService {
    private final GoodsMapper goodsMapper;

    // key 里带上 id；查不到也会缓存空值 60 秒，防止穿透
    @Cacheable(cacheNames = "goods", key = "#id", unless = "#result == null")
    public Goods detail(Long id) {
        return goodsMapper.selectById(id);
    }

    // 更新商品后删除对应缓存
    @CacheEvict(cacheNames = "goods", key = "#dto.id")
    public void update(GoodsUpdateDTO dto) {
        goodsMapper.updateById(convert(dto));
    }
}

示例二：Quartz 集群任务定义。任务类每次执行都可能被另一实例抢占，因此逻辑必须幂等：

// 任务实现：Job 由 Quartz 实例化，依赖用静态持有或 JobFactory 注入
@Slf4j
@Component
public class OrderTimeoutJob implements Job {
    @Autowired private OrderService orderService;

    @Override
    public void execute(JobExecutionContext ctx) {
        String bizKey = ctx.getJobDetail().getKey().getName();
        log.info("[超时关单] 开始 bizKey={} time={}", bizKey, LocalDateTime.now());
        // 幂等：只处理状态为"待支付"且创建超过 30 分钟的订单
        int closed = orderService.closeTimeoutOrders(Duration.ofMinutes(30));
        log.info("[超时关单] 关闭 {} 笔", closed);
    }
}

// 注册：cron 每 5 分钟一次；集群配置见 quartz.properties
@Configuration
public class QuartzConfig {
    @Bean
    public JobDetail timeoutJobDetail() {
        return JobBuilder.newJob(OrderTimeoutJob.class)
                .withIdentity("orderTimeoutJob", "order")
                .storeDurably()          // 没有触发器时也保留任务
                .build();
    }

    @Bean
    public Trigger timeoutJobTrigger() {
        return TriggerBuilder.newTrigger()
                .forJob(timeoutJobDetail())
                .withSchedule(CronScheduleBuilder.cronSchedule("0 */5 * * * ?")
                        .withMisfireHandlingInstructionDoNothing())  // 错过的执行不补跑
                .build();
    }
}
💡 提示：排查缓存问题时先用 redis-cli 的 OBJECT ENCODING 和 TTL 看看 key 的真实形态；排查定时任务重复执行时，先确认是不是多实例部署却仍用 @Scheduled。

四、实践任务

  1. 任务 1：为项目中的字典表查询加上 @Cacheable，改造更新接口加 @CacheEvict，用 redis-cli 验证 key 命名、TTL 和 JSON 序列化结果。
  2. 任务 2：写一个压测脚本（如 ab 或 JMeter）对比加缓存前后接口的 QPS 与数据库 CPU 变化，记录数字。
  3. 任务 3：实现"缓存空值防穿透"：查询不存在的 id 时缓存空对象 60 秒，验证第二次请求不再打到数据库。
  4. 任务 4（进阶，可选）：注册一个 Quartz 任务（如每小时清理过期数据），加上 quartz.properties 配置数据库集群模式，并说明为什么任务方法要幂等。
