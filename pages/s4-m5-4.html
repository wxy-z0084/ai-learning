容量规划与弹性伸缩

预计 0.5 天模块五 · 高并发系统落地

一、学习目标

  • 能够基于压测得出的单机容量数据，用公式推算出目标峰值下的机器数量并留出合理冗余。
  • 能够看懂 CPU 利用率、内存、连接池、带宽四个维度的容量水位，并设定扩容触发线。
  • 能够为在线与离线两类负载设计弹性伸缩策略（定时、阈值、预测式），并处理伸缩期间的流量衔接。

二、核心知识点

知识点 1：容量规划的公式与冗余

容量规划的输入只有一个：压测测出来的单机处理能力（比如单实例稳定承载 300 TPS）。公式很简单：机器数 = 目标峰值 TPS ÷ 单机容量 × 安全系数。安全系数通常取 1.5-2（大促取 2），它同时覆盖了流量预估误差、机器故障和长尾延迟劣化。示例：目标峰值 5000 TPS、单机 300 TPS、系数 1.7，需要 5000÷300×1.7≈29 台，按最小扩容粒度取 32 台。

比数字更重要的是短板原则：整体容量由最稀缺的资源决定——CPU 先打满、连接池先耗尽还是带宽先跑满，取最先到的那个。所以规划时要同时给出 CPU、内存、连接数、带宽四个维度的测算表，而不是只算 CPU。

知识点 2：容量水位线的设定

给每类资源画三条线：警戒线（如 CPU 60%，提前准备）、扩容线（70%，触发自动扩容）、熔断线（85%，触发限流保命）。为什么不直接 90% 才扩？因为扩容动作本身有延迟：新机器拉起、镜像分发、预热、注册到负载均衡，传统 VM 分钟级，容器冷启动也要几十秒到几分钟，这段时间里流量还在涨。此外，刚启动的实例有JIT 预热问题，前几分钟处理能力打折，要靠负载均衡的预热配置（新实例先接少量流量）来平滑。

另一个常被忽略的容量项是下游容量

知识点 3：弹性伸缩的三种策略与衔接

定时伸缩适合已知峰值（大促、发版直播），提前 30 分钟扩容，最可靠；阈值伸缩适合日常波动（按 CPU 或队列积压自动加减），但要配置冷却时间（缩容后 10-15 分钟内不再缩，防止抖动来回震荡）；预测式伸缩结合历史同期数据提前动作，云厂商均已提供（如 AWS Predictive Scaling、阿里云弹性伸缩的定时规则）。

伸缩期间的衔接设计是重点：缩容前必须先摘流量（从负载均衡下线 → 等待存量请求处理完 → 再关机），否则正在处理的请求会直接失败；无状态服务最好做，有状态服务（WebSocket、长连接 AI 会话）缩容要格外小心，需要迁移会话或采用分片摘除策略。

三、示例演示

示例一：容量测算表（可直接套用到 Excel），把"拍脑袋买机器"变成有依据的推算：

# capacity_plan.py —— 容量测算（可直接运行）
peak_tps      = 5000          # 业务预估峰值（来自历史大促数据 × 增长系数）
single_cap    = 300           # 单实例压测稳定容量（来自上一节压测报告）
safety_factor = 1.7           # 安全系数：覆盖预估误差 + 故障 + 预热打折

import math
nodes = math.ceil(peak_tps / single_cap * safety_factor)
print(f"应用实例数: {nodes} 台")                 # 输出 29

# 短板维度并行核算
db_conn_per_node = 50
print(f"数据库连接池总需求: {nodes * db_conn_per_node} 个")  # 提前告知 DBA 扩容
bandwidth_mbps   = nodes * 50
print(f"出口带宽需求: {bandwidth_mbps} Mbps")

示例二：Kubernetes HPA + 缩容前优雅摘流量的配置要点（无状态在线服务）：

# hpa.yaml —— CPU 扩容线 70%，副本 4~20，含缩容冷却
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
spec:
  scaleTargetRef: {apiVersion: apps/v1, kind: Deployment, name: order-service}
  minReplicas: 4
  maxReplicas: 20
  metrics:
    - type: Resource
      resource: {name: cpu, target: {type: Utilization, averageUtilization: 70}}
  behavior:
    scaleDown:
      stabilizationWindowSeconds: 900    # 缩容冷却 15 分钟，防抖动
---
# 关键配套：preStop 钩子 + terminationGracePeriodSeconds
# 先从 Endpoint 摘除（停止接新流量）→ 等 15 秒让存量请求跑完 → 再退出进程
lifecycle:
  preStop:
    exec: {command: ["sh", "-c", "sleep 15"]}
💡 提示：每次大促前做一次"缩容演练"——手动砍掉 30% 机器，观察剩余实例的 CPU 与错误率。这比任何理论推算都能暴露真实的容量水位。

四、实践任务

  1. 任务 1：用容量测算脚本，为你的目标峰值（自拟）算出实例数、数据库连接数、带宽三项，并写出安全系数取 1.7 的三条理由。
  2. 任务 2：为关键资源（CPU、队列积压）各写一条扩容触发条件和一条缩容条件，注明冷却时间。
  3. 任务 3：列出你的系统里 3 个"扩容不解决问题"的依赖点（如第三方 API 配额、数据库单点），为每个写出应对方案。
  4. 任务 4（进阶，可选）：设计一次缩容演练方案，包含演练目标、步骤、观察指标和回退条件。

六、自检清单

  • 我的扩容数量是否有压测数据支撑，而不是凭经验估计？
  • 我是否同时核算了 CPU、内存、连接池、带宽四个维度？
  • 我的伸缩策略是否考虑了扩容延迟和 JIT 预热带来的能力折扣？
  • 缩容时我的系统能否做到先摘流量再关机，不中断存量请求？
