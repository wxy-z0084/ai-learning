阶段四 · 业务解决方案

消息队列（RabbitMQ / Kafka）

预计 1 天模块二 · 分布式方案

一、学习目标

  • 能够说清消息队列解决的三类问题（异步、解耦、削峰），并判断一个业务点该不该上 MQ。
  • 能够用 RabbitMQ 实现可靠投递：生产端 confirm、队列与消息持久化、消费端手动 ACK 与重回队列策略。
  • 能够解释 Kafka 的 topic / partition / offset / consumer group 概念，说明分区数与消费并行度、顺序性的关系。
  • 能够在 RabbitMQ 与 Kafka 之间做选型，并设计防重复消费（幂等）与积压告警的基本方案。

二、核心知识点

知识点 1：MQ 的三个经典用途与代价

异步：下单后发短信、记流水这类非主链路操作移出主流程，接口响应时间从串行 300ms 降到 50ms。解耦：订单创建后需要通知库存、积分、物流三个系统，用一条消息广播，后续新增订阅方无需改订单服务代码。削峰：秒杀请求先入队，下游按自身处理能力慢慢消费，保护数据库不被瞬时洪峰打挂。

代价同样要认清：引入 MQ 后链路变长，排查问题要看两套日志（所以才需要上一节的分布式追踪）；消息可能丢失、重复、乱序，必须分别设计对策；集群本身要运维（磁盘、监控、多副本）。判断标准很简单——若一个操作必须同步返回明确结果（如支付扣款），不要丢给 MQ；若允许"先受理、后处理"，才适合异步化。

知识点 2：RabbitMQ 与可靠性投递

RabbitMQ 是传统消息代理（Broker）模型：消息经交换机（Exchange，类型有 direct / topic / fanout / headers）路由到队列（Queue），再投递给消费者。它的优势是路由灵活、确认机制精细，天然支持工作队列、发布订阅、RPC 等多种模式，单条消息可被多个队列独立消费。

可靠性要三段保障：生产端开启 publisher confirm，确认消息已落 Broker；队列与消息设置持久化（durable 队列 + deliveryMode=2），否则 Broker 重启消息即丢；消费端用手动 ACK，业务处理成功后再确认，处理失败则 nack + requeue 或进死信队列（DLX）人工处理。注意：手动 ACK 若忘记确认，消息会一直重投造成重复消费——消费逻辑必须按消息唯一 ID 幂等。老版本的镜像队列正被 Quorum Queue（基于 Raft）取代，新项目直接用后者。

知识点 3：Kafka 的日志模型与消费语义

Kafka 把每个分区（Partition）实现为一个只追加的提交日志（commit log），消息按写入顺序分配递增的 offset，消费者自己记录读到哪个 offset。这种设计带来三个关键特性：超高吞吐（顺序写磁盘 + 零拷贝）、多消费者组互不影响（每个组独立读全量）、以及天然的回溯消费能力（可把 offset 调到任意位置重放，常用于数据订正和新系统上线回灌历史数据）。

必须吃透的三条规则：顺序性只在分区内保证——同一业务单号要发到同一分区（自定义分区器或用业务键做 key），并保证该分区内同单号消息由同一个消费者实例处理；消费并行度 = 分区数，消费者组内实例超过分区数会有实例空闲；重复消费无法根除（至少一次语义：offset 提交与业务处理不是原子的），下游必须按 key 幂等。rebalance（消费者组重平衡）瞬间可能造成重复或停顿，大流量场景可开启静态成员资格（static membership）缓解。

三、示例演示

示例一：RabbitMQ 可靠投递的 Python 生产者（pika，生产确认模式）与消费者（手动 ACK）：

# producer.py —— pip install pika
import pika, json

creds = pika.PlainCredentials("guest", "guest")
params = pika.ConnectionParameters("localhost", 5672, "/", creds)
conn = pika.BlockingConnection(params)
ch = conn.channel()
ch.confirm_delivery()                       # 开启生产确认
ch.queue_declare(queue="order.created", durable=True)  # 持久化队列

ch.basic_publish(
    exchange="", routing_key="order.created",
    body=json.dumps({"orderId": "A1001", "amount": 99.0}),
    properties=pika.BasicProperties(delivery_mode=2),  # 持久化消息
    mandatory=True)
conn.close()
# consumer.py —— 手动 ACK，处理失败重回队列
import pika, json, time

def on_message(ch, method, properties, body):
    msg = json.loads(body)
    try:
        handle_order(msg)          # 幂等：按 orderId 去重
        ch.basic_ack(delivery_tag=method.delivery_tag)
    except Exception:
        # 不 requeue 可配合死信队列转人工，避免毒消息无限循环
        ch.basic_nack(delivery_tag=method.delivery_tag, requeue=True)

conn = pika.BlockingConnection(
    pika.ConnectionParameters("localhost", 5672, "/", pika.PlainCredentials("guest", "guest")))
ch = conn.channel()
ch.queue_declare(queue="order.created", durable=True)
ch.basic_qos(prefetch_count=10)    # 一次拉取 10 条，防止被单条慢消息卡住
ch.basic_consume(queue="order.created", on_message_callback=on_message)
ch.start_consuming()
💡 本地实验推荐用 docker 快速拉起两个 Broker：docker run -d --name rabbitmq -p 5672:5672 -p 15672:25672 rabbitmq:3-management（管理界面 http://localhost:15672），以及 docker run -d --name kafka apache/kafka:3.7.0。看懂管理界面里的 unacked、ready、messages 学习曲线最陡也最有用的三个指标。

示例二：Kafka 生产者与消费者组（confluent-kafka 库），演示按业务键分区与 offset 提交：

# pip install confluent-kafka
from confluent_kafka import Consumer, Producer, KafkaError

# 生产端：key 相同则进入同一分区，保证单订单有序
p = Producer({"bootstrap.servers": "localhost:9092"})
p.produce("order.created", key=b"A1001",
          value=b'{"orderId":"A1001","amount":99.0}')
p.flush(10)

# 消费端：手动提交 offset，业务先幂等再提交
c = Consumer({"bootstrap.servers": "localhost:9092",
              "group.id": "order-group-1",   # 同组分摊分区，异组各自全量
              "enable.auto.commit": False})
c.subscribe(["order.created"])
while True:
    msg = c.poll(1.0)
    if msg is None or msg.error():
        if msg and msg.error().code() == KafkaError._PARTITION_EOF:
            continue
        continue
    process(msg.key().decode(), msg.value().decode())  # 内部按 key 幂等
    c.commit(message=msg)                               # 业务成功后再提交 offset

四、实践任务

  1. 任务 1：用 docker 启动 RabbitMQ，跑通上面生产者/消费者示例；在消费者里故意抛异常 3 次，观察 requeue 与消息重复投递现象，验证幂等逻辑有效。
  2. 任务 2：启动单节点 Kafka，创建 6 分区的 order.created 主题，起 2 个消费者组各 3 个消费者，用 kafka-consumer-groups.sh --describe 观察分区分配；再把消费者缩到 2 个，观察 rebalance。
  3. 任务 3：压测你的 RabbitMQ 链路（可用 perf 工具或自己写循环发 10 万条），记录开启/关闭 confirm 与持久化时的吞吐差异，把结论写成一段选型说明。
  4. 任务 4（进阶，可选）：给 order.created 配置死信队列：让消费者 nack(requeue=False) 后消息进入 DLQ，写一个小脚本从 DLQ 捞消息回放。
